## 1. 개요 + 철학

### 1.1 ADPL이란?

**ADPL (AutoDev Pipeline Description Language)** 은 AutoDev Agent 의 파이프라인 실행 동작을 YAML 로 선언하는 언어다. 개발자는 ADPL 파이프라인 파일 하나로 AI 에이전트 호출, 쉘 명령, HTTP 요청, 조건 분기, 병렬 실행 등을 조합하여 반복 가능한 자동화 워크플로를 정의한다.

ADPL 은 AutoDev 의 기존 단일 Task → Plan → Code → Verify 파이프라인을 일반화한 것이다. v1.0 에서는 단일 파이프라인 실행 모드(`pipelineMode: "pipeline"`)를 정의하며, 이후 버전에서 조직 수준 오케스트레이션, 멀티 워크트리 병렬 실행 등으로 확장된다.

### 1.2 핵심 철학

**선언적 YAML 우선**

파이프라인의 "무엇을 할 것인가"와 "어떻게 실행할 것인가"를 분리한다. ADPL 파일은 의도를 선언하며, 실행 엔진이 스케줄링·재시도·에러 처리를 담당한다. 이로써 파이프라인 정의는 실행 환경과 독립적으로 버전 관리·공유·재사용된다.

**언어와 엔진 분리**

ADPL 스펙(이 문서)과 ADPL 엔진 구현은 별개다. 동일한 ADPL 파일을 다른 엔진(예: 로컬 runner, CI 시스템)에서 실행할 수 있도록 인터페이스를 명세한다. 엔진은 스펙을 준수해야 하며, 스펙에 정의되지 않은 동작은 구현 정의(implementation-defined)다.

**확장 가능한 노드 타입**

v1.0 은 `agent`, `shell`, `http`, `webhook_out`, `branch`, `parallel`, `loop`, `gate`, `mcp`, `set` 노드를 기본 제공한다. 향후 플러그인 시스템(v1.5+)을 통해 사용자 정의 노드를 등록할 수 있다. 커스텀 노드는 기본 노드와 동일한 스키마 인터페이스를 준수해야 한다.

**Strangler Fig 패턴으로 legacy 공존**

ADPL 파이프라인 모드(`pipelineMode: "pipeline"`)는 기존 단일 Task 실행 모드(`pipelineMode: "legacy"`)와 공존한다. 기존 Task 는 ADPL 파이프라인 없이도 계속 동작하며, 새 Task 만 ADPL 을 사용하도록 점진적으로 마이그레이션할 수 있다.

### 1.3 Hello World 예시

가장 단순한 ADPL 파이프라인 — 단일 에이전트 호출:

```yaml
adplVersion: 1
name: hello-world
description: 단순한 에이전트 호출 예시

triggers:
  - type: manual

pipeline:
  - id: greet
    type: agent
    prompt: "안녕하세요! 현재 날짜와 간단한 인사말을 작성해주세요."
```

조건 분기를 포함한 예시:

```yaml
adplVersion: 1
name: conditional-review
description: 코드 품질에 따라 분기하는 예시

triggers:
  - type: manual

pipeline:
  - id: analyze
    type: agent
    prompt: "다음 코드를 분석하고 품질 점수(0-100)를 JSON으로 반환해주세요: ${$task.prompt}"
    output:
      schema:
        score: number

  - id: route
    type: branch
    branches:
      - when:
          field: $nodes.analyze.output.data.score
          gte: 80
        goto: approve
      - when:
          field: $nodes.analyze.output.data.score
          lt: 80
        goto: fix

  - id: approve
    type: agent
    prompt: "코드 품질이 양호합니다. 최종 승인 메시지를 작성해주세요."

  - id: fix
    type: agent
    prompt: "코드 품질 개선이 필요합니다. 개선 사항을 구체적으로 제안해주세요."
```

### 1.4 언제 ADPL을 쓰나

| 사용 사례 | 설명 |
|-----------|------|
| **반복 워크플로 자동화** | 코드 리뷰 → 테스트 → 배포 등 정형화된 순서를 파이프라인으로 정의 |
| **조건 분기 처리** | 결과에 따라 다른 에이전트 경로를 선택 (예: 품질 통과/실패 분기) |
| **병렬 에이전트 실행** | 독립적인 작업을 병렬로 처리하여 실행 시간 단축 |
| **외부 시스템 연동** | HTTP 엔드포인트 호출, Webhook 발송, MCP 서버 연동 |

ADPL 을 사용하지 **않는** 경우: 단발성 Task, 간단한 질의응답, 실험적 프롬프트 테스트는 기존 단일 Task 모드로 충분하다.

### 1.5 용어집

| 용어 | 정의 |
|------|------|
| **pipeline** | ADPL 파일 하나가 정의하는 실행 단위. 여러 노드의 순서 있는 집합. |
| **node** | 파이프라인의 최소 실행 단위. `agent`, `shell`, `http` 등 타입을 가짐. |
| **trigger** | 파이프라인 실행을 시작하는 이벤트. `manual`, `webhook`, `schedule` 등. |
| **flow** | `branch`, `parallel`, `loop`, `gate` 등 흐름 제어 노드의 총칭. |
| **adapter** | 외부 시스템(Slack, GitHub 등)과 AutoDev 를 연결하는 플러그인 컴포넌트. |
| **context** | 파이프라인 실행 중 노드가 참조할 수 있는 런타임 변수 집합 (`$task`, `$nodes` 등). |
| **expression** | ADPL 의 값 참조·조건 평가 언어. 3-slot 시스템으로 구성됨. |
| **version** | 동일 파이프라인 이름의 특정 YAML 스냅샷. `pipelineVersions` 테이블에 저장. |
| **project** | AutoDev 의 최상위 작업 단위. 여러 Task 와 파이프라인 버전을 포함. |

## 2. Top-level structure

ADPL 파이프라인 파일의 최상위 구조:

```yaml
adplVersion: 1              # 필수: ADPL 스펙 버전
name: my-pipeline           # 필수: 파이프라인 이름 (프로젝트 내 unique)
description: "..."          # 선택: 파이프라인 설명
triggers:                   # 선택: 실행 트리거 목록 (기본값: manual 1개)
  - type: manual
pipeline:                   # 필수: 노드 배열
  - id: step1
    type: agent
    prompt: "..."
settings:                   # 선택: 파이프라인 레벨 설정
  maxParallel: 3
  totalTimeout: 3600
metadata:                   # 선택: 자유 형식 메타데이터
  owner: team-a
  tags: [review, automation]
```

**최상위 필드 요약**:

| 필드 | 타입 | 필수 | 기본값 |
|------|------|------|--------|
| `adplVersion` | `integer` | 예 | — |
| `name` | `string` | 예 | — |
| `description` | `string` | 아니오 | `""` |
| `triggers` | `array` | 아니오 | `[{ type: manual }]` |
| `pipeline` | `array` | 예 | — |
| `settings` | `object` | 아니오 | 각 필드 기본값 |
| `metadata` | `object` | 아니오 | `{}` |

### 2.1 `adplVersion`

| 항목 | 값 |
|------|-----|
| **타입** | `integer` |
| **필수** | 예 |
| **허용 값** | `1` (v1.0 현재 유일) |
| **기본값** | 없음 (명시 필수) |

`adplVersion` 은 이 파일이 준수하는 ADPL 스펙의 Major 버전을 지정한다. 엔진은 `adplVersion` 값을 확인하여 호환 여부를 판단한다. 지원하지 않는 버전이면 실행을 거부하고 에러를 반환한다.

```yaml
adplVersion: 1
```

> ⚠️ `adplVersion` 필드가 없으면 엔진은 경고를 출력하고 latest 버전으로 해석한다. 명시적 선언을 강권한다.

### 2.2 `name`

| 항목 | 값 |
|------|-----|
| **타입** | `string` |
| **필수** | 예 |
| **허용 값** | `/^[a-z0-9][a-z0-9\-]{0,62}$/` (소문자 알파벳, 숫자, 하이픈, 63자 이하) |
| **기본값** | 없음 |
| **유일성** | 동일 `projectId` 내에서 unique |

파이프라인의 식별자. 버전 관리의 기준이 되므로, 한 번 정해진 이름은 변경하지 않는 것을 권장한다. 이름 변경은 새 파이프라인 생성과 동등하게 취급된다.

```yaml
name: code-review-pipeline
```

### 2.3 `description`

| 항목 | 값 |
|------|-----|
| **타입** | `string` |
| **필수** | 아니오 |
| **최대 길이** | 500자 |
| **기본값** | `""` (빈 문자열) |

사람이 읽기 위한 파이프라인 설명. UI 목록 표시, 검색 등에 활용된다. YAML 멀티라인 문자열 허용.

```yaml
description: |
  코드 품질을 분석하고 개선 사항을 자동으로 제안하는 파이프라인.
  품질 점수 80 미만 시 자동 수정 에이전트를 실행합니다.
```

### 2.4 `triggers`

| 항목 | 값 |
|------|-----|
| **타입** | `array<TriggerObject>` |
| **필수** | 아니오 |
| **기본값** | `[{ type: manual }]` |
| **최소 항목** | 0 (빈 배열 허용, 단 실행 불가) |

파이프라인 실행을 시작하는 이벤트 목록. 여러 트리거를 동시에 정의할 수 있다.

지원 트리거 타입:

| 타입 | 설명 |
|------|------|
| `manual` | 사용자가 UI 또는 API 를 통해 직접 실행 |
| `webhook` | 외부 HTTP POST 요청 수신 |
| `schedule` | cron 표현식 기반 정기 실행 |
| `task_event` | Task 상태 변경 이벤트 (예: Task 완료 시) |

트리거 상세 스펙은 [§15 Triggers](#15-triggers) (Part C) 참조.

```yaml
triggers:
  - type: manual
  - type: schedule
    cron: "0 9 * * 1-5"
    timezone: Asia/Seoul
```

### 2.5 `pipeline`

| 항목 | 값 |
|------|-----|
| **타입** | `array<NodeObject>` |
| **필수** | 예 |
| **최소 항목** | 1 |
| **순서** | 정의 순서대로 실행 (flow 노드가 분기/병렬 결정) |

파이프라인을 구성하는 노드의 배열. 각 노드는 `id` 와 `type` 을 필수로 가진다.

**공통 노드 필드**:

| 필드 | 타입 | 필수 | 기본값 | 설명 |
|------|------|------|--------|------|
| `id` | `string` | 예 | — | 파이프라인 내 unique 식별자 (`/^[a-z0-9][a-z0-9\-_]{0,62}$/`) |
| `type` | `string` | 예 | — | 노드 타입 (`agent`, `shell`, `http`, ...) |
| `name` | `string` | 아니오 | `id` 값 | 사람이 읽기 위한 표시 이름 |
| `description` | `string` | 아니오 | `""` | 노드 설명 |
| `when` | `Condition` | 아니오 | 항상 실행 | 실행 조건 (Slot 2 표현식) |
| `onFailure` | `FailurePolicy` | 아니오 | 파이프라인 설정 상속 | 실패 시 정책 |
| `timeout` | `integer` | 아니오 | `settings.nodeTimeout` | 노드 단위 타임아웃 (초) |
| `retryPolicy` | `RetryPolicy` | 아니오 | 없음 | 재시도 설정 |
| `dependsOn` | `string[]` | 아니오 | `[]` | 명시적 의존 노드 목록 |

```yaml
pipeline:
  - id: plan
    type: agent
    prompt: "구현 계획을 수립해주세요: ${$task.prompt}"

  - id: implement
    type: agent
    prompt: "다음 계획을 구현해주세요: ${$nodes.plan.output.data}"
    dependsOn: [plan]

  - id: verify
    type: shell
    command: "pnpm test"
    dependsOn: [implement]
```

### 2.6 `settings`

| 항목 | 값 |
|------|-----|
| **타입** | `object` |
| **필수** | 아니오 |
| **기본값** | 아래 각 필드 기본값 참조 |

파이프라인 레벨 실행 설정. 노드 단위 설정이 우선한다.

| 필드 | 타입 | 기본값 | 허용 범위 | 설명 |
|------|------|--------|-----------|------|
| `maxParallel` | `integer` | `5` | 1–20 | 동시 실행 가능한 최대 노드 수 |
| `totalTimeout` | `integer` | `7200` | 1–86400 | 파이프라인 전체 타임아웃 (초) |
| `nodeTimeout` | `integer` | `600` | 1–3600 | 노드 단위 기본 타임아웃 (초) |
| `onNodeFailure` | `FailurePolicy` | `"abort"` | abort\|continue\|retry | 노드 실패 시 기본 정책 |
| `totalCostLimit` | `number \| null` | `null` | > 0 | 파이프라인 총 비용 한도 (USD) |
| `retryPolicy` | `RetryPolicy \| null` | `null` | — | 파이프라인 기본 재시도 정책 |
| `allowedEnvKeys` | `string[]` | `[]` | — | `$env` 에서 접근 허용된 환경 변수 키 목록 |

`FailurePolicy` 허용 값:

| 값 | 동작 |
|----|------|
| `"abort"` | 파이프라인 즉시 중단, 후속 노드 실행 안 함 |
| `"continue"` | 실패 노드를 `skipped` 로 표시하고 후속 노드 계속 실행 |
| `"retry"` | `retryPolicy` 에 따라 재시도 후 실패 시 `abort` |

`RetryPolicy` 스키마:

```yaml
retryPolicy:
  maxAttempts: 3        # 최대 시도 횟수 (초기 실행 포함, 기본값: 1)
  backoff: exponential  # linear | exponential | fixed
  initialDelay: 5       # 첫 재시도 대기 시간 (초)
  maxDelay: 60          # 최대 대기 시간 (초)
```

```yaml
settings:
  maxParallel: 3
  totalTimeout: 3600
  onNodeFailure: continue
  totalCostLimit: 1.00
  allowedEnvKeys:
    - GITHUB_TOKEN
    - SLACK_WEBHOOK_URL
```

### 2.7 `metadata`

| 항목 | 값 |
|------|-----|
| **타입** | `object` (자유 형식) |
| **필수** | 아니오 |
| **기본값** | `{}` |

엔진이 해석하지 않는 자유 형식 메타데이터. UI 표시, 태깅, 외부 시스템 연동 등에 활용한다.

```yaml
metadata:
  owner: platform-team
  tags:
    - code-quality
    - automation
  version: "2.1.0"
```

> ⚠️ `metadata` 의 값은 ADPL 표현식으로 평가되지 않는다. 정적 값만 허용한다.

### 2.8 전체 예시

필드 조합의 전형적인 예:

```yaml
adplVersion: 1
name: full-review-pipeline
description: 코드 리뷰 + 자동 수정 + 검증 파이프라인

triggers:
  - type: manual
  - type: webhook
    secret: "${$env.WEBHOOK_SECRET}"

pipeline:
  - id: review
    type: agent
    prompt: |
      다음 코드를 리뷰하고 JSON 형식으로 결과를 반환해주세요.
      코드: ${$task.prompt}
    output:
      schema:
        score: number
        issues: array

  - id: check-quality
    type: branch
    branches:
      - when:
          field: $nodes.review.output.data.score
          gte: 80
        goto: approve
      - else: true
        goto: fix

  - id: fix
    type: agent
    prompt: "다음 이슈를 수정해주세요: ${$nodes.review.output.data.issues | json}"

  - id: approve
    type: shell
    command: "echo 'Quality passed'"

settings:
  maxParallel: 2
  totalTimeout: 1800
  onNodeFailure: abort
  totalCostLimit: 0.50

metadata:
  owner: code-quality-team
  tags: [review, automated]
```

## 3. 컨텍스트 변수

파이프라인 실행 중 모든 표현식에서 접근 가능한 런타임 변수 집합. 네임스페이스(`$task`, `$nodes` 등)로 구분된다.

### 3.1 `$task`

현재 실행 중인 Task 의 정보. 파이프라인 실행 전체에서 접근 가능.

| 필드 | 타입 | 설명 |
|------|------|------|
| `$task.id` | `string` | Task 고유 ID (nanoid) |
| `$task.prompt` | `string` | Task 에 입력된 원본 프롬프트 |
| `$task.tags` | `string[]` | Task 태그 목록 |
| `$task.createdAt` | `string` | Task 생성 시각 (ISO 8601) |
| `$task.pipelineMode` | `string` | `"pipeline"` 또는 `"legacy"` |
| `$task.projectId` | `string \| null` | 연결된 프로젝트 ID |
| `$task.pipelineVersionId` | `string \| null` | 실행 중인 파이프라인 버전 ID |
| `$task.status` | `string` | 현재 Task 상태 |
| `$task.config` | `object` | Task 생성 시 전달된 설정 객체 |

```yaml
- id: process
  type: agent
  prompt: "다음 요청을 처리해주세요: ${$task.prompt}"
```

### 3.2 `$project`

현재 Task 가 속한 Project 의 정보.

| 필드 | 타입 | 설명 |
|------|------|------|
| `$project.id` | `string` | 프로젝트 고유 ID |
| `$project.name` | `string` | 프로젝트 이름 |
| `$project.path` | `string` | 프로젝트 루트 절대 경로 |
| `$project.description` | `string \| null` | 프로젝트 설명 |
| `$project.createdAt` | `string` | 프로젝트 생성 시각 (ISO 8601) |

> ⚠️ `$task.projectId` 가 `null` 이면 `$project` 의 모든 필드는 `null` 을 반환한다.

```yaml
- id: analyze
  type: agent
  prompt: "프로젝트 ${$project.name} (${$project.path}) 의 코드를 분석해주세요."
```

### 3.3 `$nodes`

완료된 노드의 실행 결과에 접근한다. **가장 중요한 컨텍스트 네임스페이스**.

```
$nodes.<nodeId>.output.status    # "success" | "failure" | "skipped"
$nodes.<nodeId>.output.data      # 노드가 반환한 데이터 (노드 타입별 상이)
$nodes.<nodeId>.output.error     # 실패 시 에러 정보 (status = "failure" 일 때)
$nodes.<nodeId>.output.duration  # 실행 소요 시간 (ms)
$nodes.<nodeId>.output.costUsd   # agent 노드의 경우 비용 (USD)
```

**접근 규칙**:

| 규칙 | 설명 |
|------|------|
| **순서 제약** | 현재 노드보다 **앞에 정의된 노드**만 접근 가능 |
| **완료 상태** | `status` 가 `success`, `failure`, `skipped` 인 노드만 접근 가능 |
| **pending/running 접근** | 에러: `ReferenceError: node 'X' is not yet completed` |
| **미존재 노드 접근** | 저장 단계에서 검증 실패 (Compile time error) |

**`output.data` 타입**:

| 노드 타입 | `output.data` 타입 |
|-----------|---------------------|
| `agent` | `string` 또는 `output.schema` 정의 시 해당 구조 |
| `shell` | `{ stdout: string, stderr: string, exitCode: number }` |
| `http` | `{ status: number, headers: object, body: unknown }` |
| `set` | 설정된 변수 값 |

```yaml
- id: plan
  type: agent
  prompt: "구현 계획을 수립해주세요."

- id: implement
  type: agent
  prompt: |
    다음 계획을 구현해주세요:
    ${$nodes.plan.output.data}
  when:
    field: $nodes.plan.output.status
    eq: success
```

### 3.4 `$loop`

`loop` 노드 내부의 노드에서만 접근 가능. 현재 반복 컨텍스트를 제공한다.

| 필드 | 타입 | 설명 |
|------|------|------|
| `$loop.index` | `integer` | 현재 반복 인덱스 (0부터 시작) |
| `$loop.total` | `integer` | 총 반복 횟수 |
| `$loop.isFirst` | `boolean` | 첫 번째 반복 여부 |
| `$loop.isLast` | `boolean` | 마지막 반복 여부 |
| `$loop.<as>` | `unknown` | `loop.as` 로 지정한 이름의 현재 아이템 |

> ⚠️ `loop` 노드 외부에서 `$loop` 접근 시 에러: `ReferenceError: $loop is not available outside a loop node`

```yaml
- id: process-items
  type: loop
  items: "${$task.config.files}"
  as: file
  pipeline:
    - id: analyze-file
      type: agent
      prompt: |
        파일 ${$loop.index + 1}/${$loop.total}: ${$loop.file}
        이 파일을 분석해주세요.
```

### 3.5 `$flow`

`branch`, `parallel`, `gate` 등 flow 노드 내부에서 추가 컨텍스트를 제공한다.

**`branch` 내부**:

| 필드 | 타입 | 설명 |
|------|------|------|
| `$flow.matchedBranch` | `string` | 선택된 branch 의 `id` 또는 인덱스 |

**`parallel` 내부**:

| 필드 | 타입 | 설명 |
|------|------|------|
| `$flow.parallelIndex` | `integer` | 병렬 실행 중 현재 브랜치 인덱스 |
| `$flow.parallelTotal` | `integer` | 병렬 실행 총 브랜치 수 |

**`gate` 내부**:

| 필드 | 타입 | 설명 |
|------|------|------|
| `$flow.gateStatus` | `string` | `"pending"` \| `"approved"` \| `"rejected"` |
| `$flow.gateRespondedBy` | `string \| null` | 승인/거절한 사용자 ID |

### 3.6 `$env`

프로젝트 또는 시스템 레벨에서 설정된 환경 변수에 접근한다.

**접근 규칙**:

| 규칙 | 설명 |
|------|------|
| **Allowlist 필수** | `settings.allowedEnvKeys` 에 포함된 키만 접근 가능 |
| **미승인 키 접근** | 에러: `SecurityError: env key 'X' is not in allowedEnvKeys` |
| **미존재 키** | `null` 반환 (에러 아님) |
| **로그 마스킹** | `$env.*` 값은 로그·UI 에서 자동으로 `***` 로 마스킹 |

```yaml
settings:
  allowedEnvKeys:
    - GITHUB_TOKEN

pipeline:
  - id: github-api
    type: http
    url: "https://api.github.com/repos/owner/repo"
    headers:
      Authorization: "Bearer ${$env.GITHUB_TOKEN}"
```

### 3.7 `$trigger`

파이프라인을 실행시킨 트리거의 정보.

**공통 필드**:

| 필드 | 타입 | 설명 |
|------|------|------|
| `$trigger.type` | `string` | 트리거 타입 (`manual`, `webhook`, `schedule`, `task_event`) |
| `$trigger.firedAt` | `string` | 트리거 발동 시각 (ISO 8601) |

**`webhook` 트리거 추가 필드**:

| 필드 | 타입 | 설명 |
|------|------|------|
| `$trigger.payload` | `object` | HTTP 요청 body (JSON 파싱된 값) |
| `$trigger.headers` | `object` | HTTP 요청 헤더 (소문자 키) |
| `$trigger.sourceIp` | `string` | 요청 발신 IP |

**`schedule` 트리거 추가 필드**:

| 필드 | 타입 | 설명 |
|------|------|------|
| `$trigger.scheduledAt` | `string` | cron 스케줄 기준 실행 예정 시각 (ISO 8601) |

```yaml
- id: handle-webhook
  type: agent
  prompt: |
    ${$trigger.payload.event} 이벤트를 처리해주세요.
    페이로드: ${$trigger.payload | json}
```

## 4. 표현식 3-slot 시스템

ADPL 은 세 가지 표현식 슬롯을 제공한다. 각 슬롯은 사용 위치와 목적이 다르다.

| 슬롯 | 이름 | 문법 | 주요 사용 위치 |
|------|------|------|---------------|
| Slot 1 | 보간 (Interpolation) | `${...}` | 문자열 값 안 |
| Slot 2 | 조건 (Condition) | 구조화 객체 또는 문자열 | `when`, `condition`, `filter` 필드 |
| Slot 3 | 변환 (Transform) | — | **v1.5 유보** |

### 4.1 Slot 1: 보간 (Interpolation)

문자열 값 안에 `${...}` 구문으로 런타임 값을 삽입한다.

**기본 문법**:

```
${<expression>}
${<expression> | <filter>}
${<expression> | <filter1> | <filter2>}
${<expression> ?? <fallback>}
```

**예시**:

```yaml
prompt: "작업: ${$task.prompt}"
prompt: "점수: ${$nodes.review.output.data.score | round}"
prompt: "태그: ${$task.tags | join(', ')}"
prompt: "요약: ${$nodes.analyze.output.data ?? '(결과 없음)'}"
```

**내장 필터 20개**:

| 필터 | 설명 | 예시 |
|------|------|------|
| `truncate(n)` | n 자로 잘라냄 | `${text \| truncate(100)}` |
| `lower` | 소문자 변환 | `${$task.prompt \| lower}` |
| `upper` | 대문자 변환 | `${status \| upper}` |
| `json` | JSON 직렬화 | `${data \| json}` |
| `round` | 반올림 (정수) | `${score \| round}` |
| `toFixed(n)` | 소수점 n자리 | `${cost \| toFixed(4)}` |
| `replace(a, b)` | 문자열 치환 | `${text \| replace('old', 'new')}` |
| `slice(s, e)` | 배열/문자열 슬라이스 | `${list \| slice(0, 3)}` |
| `default(v)` | null/undefined 시 기본값 | `${name \| default('익명')}` |
| `join(sep)` | 배열을 문자열로 | `${tags \| join(', ')}` |
| `length` | 길이 반환 | `${text \| length}` |
| `escape` | HTML 이스케이프 | `${html \| escape}` |
| `urlencode` | URL 인코딩 | `${param \| urlencode}` |
| `jsonParse` | JSON 파싱 | `${jsonStr \| jsonParse}` |
| `toDate` | ISO 8601 → 날짜 포맷 | `${createdAt \| toDate}` |
| `toTime` | ISO 8601 → 시간 포맷 | `${firedAt \| toTime}` |
| `padStart(n, c)` | 앞 패딩 | `${num \| padStart(3, '0')}` |
| `padEnd(n, c)` | 뒤 패딩 | `${code \| padEnd(10, ' ')}` |
| `trim` | 앞뒤 공백 제거 | `${text \| trim}` |
| `capitalize` | 첫 글자 대문자 | `${name \| capitalize}` |

**Nullish Fallback (`??`)**:

표현식 결과가 `null` 또는 `undefined` 일 때 대체값을 사용한다:

```yaml
prompt: "결과: ${$nodes.analyze.output.data.summary ?? '분석 결과가 없습니다.'}"
```

> ⚠️ **삼항 연산자 없음**: `${ condition ? a : b }` 문법은 지원하지 않는다. 조건 분기는 `branch` 노드 또는 `when` 필드를 사용하라.

**Anti-pattern**:

```yaml
# ❌ 삼항 연산자 — 지원 안 함
prompt: "${score >= 80 ? '통과' : '실패'}"

# ✅ branch 노드로 분기
- id: route
  type: branch
  branches:
    - when:
        field: $nodes.review.output.data.score
        gte: 80
      goto: approve
    - else: true
      goto: reject
```

### 4.2 Slot 2: 구조화 조건 (Structured conditions)

`when`, `condition`, `filter` 필드에서 YAML/JSON 구조로 조건을 표현한다. 코드 없이 조건을 명시할 수 있어 검증·직렬화가 용이하다.

**단일 조건**:

```yaml
when:
  field: $nodes.analyze.output.data.score
  gte: 80
```

**15개 연산자**:

| 연산자 | 입력 타입 | 설명 |
|--------|-----------|------|
| `eq` | any | 같음 (`===`) |
| `neq` | any | 다름 (`!==`) |
| `lt` | number | 미만 |
| `lte` | number | 이하 |
| `gt` | number | 초과 |
| `gte` | number | 이상 |
| `in` | array | 배열 내 포함 |
| `nin` | array | 배열 내 미포함 |
| `contains` | string | 부분 문자열 포함 |
| `startsWith` | string | 특정 문자열로 시작 |
| `endsWith` | string | 특정 문자열로 끝 |
| `matches` | string (regex) | 정규식 매칭 |
| `exists` | — | null/undefined 가 아님 |
| `empty` | — | null, undefined, 빈 문자열, 빈 배열 |
| `truthy` | — | 논리적으로 참 |

**복합 조건**:

```yaml
# AND (all)
when:
  all:
    - field: $nodes.review.output.data.score
      gte: 70
    - field: $nodes.review.output.data.issues
      empty: true

# OR (any)
when:
  any:
    - field: $task.tags
      contains: urgent
    - field: $nodes.analyze.output.data.severity
      eq: critical

# NOT
when:
  not:
    field: $nodes.gate.output.status
    eq: rejected
```

**조건 내 변환 (`lower`, `upper`, `length`)**:

```yaml
when:
  field: $task.prompt
  transform: lower
  contains: "bug fix"
```

**중첩 복합 조건 예시**:

```yaml
when:
  all:
    - field: $nodes.test.output.data.exitCode
      eq: 0
    - field: $nodes.lint.output.data.errors
      transform: length
      eq: 0
    - any:
        - field: $task.tags
          in: [hotfix, urgent]
        - field: $task.config.priority
          gte: 8
```

### 4.3 Slot 2: 문자열 조건 (String conditions)

구조화 조건과 동등하며, 자연스러운 문자열 표현을 사용한다. Jexl 기반 파서(또는 자체 구현)로 평가된다.

**문법**:

```yaml
when: "$nodes.review.output.data.score >= 80"
when: "$task.tags contains 'urgent' and $nodes.plan.output.status == 'success'"
when: "$nodes.test.output.data.exitCode == 0 or $task.config.skipTest == true"
```

**허용 연산자**:

| 연산자 | 설명 |
|--------|------|
| `==`, `!=` | 동등 비교 |
| `<`, `<=`, `>`, `>=` | 크기 비교 |
| `contains` | 문자열/배열 포함 |
| `startsWith`, `endsWith` | 문자열 시작/끝 |
| `matches` | 정규식 매칭 (`/pattern/` 문법) |
| `in` | 배열 포함 (`x in [a, b, c]`) |
| `and`, `or`, `not` | 논리 연산 |
| `(...)` | 괄호 그룹 |

**허용 함수**:

| 함수 | 설명 |
|------|------|
| `length(x)` | 길이 |
| `lower(x)` | 소문자 |
| `upper(x)` | 대문자 |
| `exists(x)` | 존재 여부 |
| `empty(x)` | 빈 값 여부 |

**구조화 조건과 동등 예시**:

```yaml
# 문자열 조건
when: "$nodes.analyze.output.data.score >= 80 and $nodes.lint.output.data.errors == 0"

# 위와 동등한 구조화 조건
when:
  all:
    - field: $nodes.analyze.output.data.score
      gte: 80
    - field: $nodes.lint.output.data.errors
      eq: 0
```

**문자열 조건 추가 예시**:

```yaml
# 복합 논리
when: "(length($nodes.issues.output.data) == 0) or ($task.config.force == true)"

# 정규식 사용
when: "$task.prompt matches /^(fix|hotfix):/i"

# 배열 포함
when: "$task.tags in ['critical', 'p0', 'p1']"

# 함수 조합
when: "lower($nodes.agent.output.data) contains 'error' and exists($task.config.debug)"
```

> ⚠️ 문자열 조건은 구조화 조건보다 파싱 복잡도가 높아 저장 단계 검증이 덜 정확할 수 있다. 프로그래매틱 생성 시 구조화 조건을 권장한다.

### 4.4 Slot 3: 변환 (Transform) — v1.5 유보

> **이 슬롯은 ADPL v1.0 에서 정의하지 않는다.**

v1.0 에서 데이터 변환이 필요한 경우:

- `set` 노드로 값 설정: [§17 보조 노드](#17-보조-노드-set-transform) (Part C) 참조
- Slot 1 필터로 포맷 변환
- `agent` 노드에 변환 로직 포함

Slot 3 (`transform` 노드 타입) 은 v1.5 에서 공식 도입 예정이다.

### 4.5 표현식 사용 위치

| 위치 | Slot | 설명 |
|------|------|------|
| 문자열 필드 값 안 `${...}` | Slot 1 | `prompt`, `url`, `command`, `headers.*` 등 |
| `when` 필드 | Slot 2 | 노드 실행 조건 |
| `condition` 필드 | Slot 2 | `branch` 노드의 분기 조건 |
| `filter` 필드 | Slot 2 | `loop` 노드의 아이템 필터 |
| `items` 필드 | Slot 1 | `loop` 노드의 반복 대상 배열 (`${...}` 로 참조) |
| `goto` 필드 | — | 정적 문자열만 허용 (표현식 불가) |
| `metadata.*` | — | 표현식 미지원 (정적 값만) |

### 4.6 에러 처리

**파싱 에러 (저장 단계)**:

| 상황 | 에러 타입 | 예시 |
|------|-----------|------|
| `${` 는 있으나 `}` 없음 | `ParseError` | `${$task.prompt` |
| 미지원 필터 | `ParseError` | `${text \| unknownFilter}` |
| Slot 2 문자열 문법 오류 | `ParseError` | `when: "score > "` |
| `$nodes.X` — X 가 파이프라인에 없음 | `ReferenceError` | `$nodes.nonexistent` |

**런타임 에러**:

| 상황 | 에러 타입 | 기본 동작 |
|------|-----------|-----------|
| `$nodes.X` 에서 X 가 아직 완료 안 됨 | `ReferenceError` | 파이프라인 실패 |
| 타입 미스매치 (예: 숫자 필터를 문자열에) | `TypeError` | `onFailure` 정책에 따름 |
| `$env.X` 가 allowlist 에 없음 | `SecurityError` | 파이프라인 실패 |
| `$env.X` 가 존재하지 않음 | — | `null` 반환 (에러 아님) |
| `$loop.*` 를 loop 외부에서 접근 | `ReferenceError` | 파이프라인 실패 |

**복구 정책**:

- **Slot 1 보간 에러**: 기본적으로 파이프라인 실패 (`abort`). `?? fallback` 을 사용하면 런타임 에러 대신 fallback 값 사용.
- **Slot 2 조건 에러**: 기본적으로 조건이 `false` 로 평가 (파이프라인은 계속 실행). 단, `ReferenceError` 와 `SecurityError` 는 파이프라인을 실패시킨다.

```yaml
# ?? fallback 으로 런타임 에러 방지
prompt: "이전 결과: ${$nodes.prev.output.data.summary ?? '결과 없음'}"
```

## 5. 에러 + 검증 규칙

ADPL 검증은 **저장 단계 (Compile time)** 와 **런타임 단계 (Run time)** 두 단계로 이루어진다.

### 5.1 저장 단계 검증 (Compile time)

파이프라인 YAML 을 저장·등록할 때 수행하는 정적 검증.

**5.1.1 YAML 파싱**

유효한 YAML 문법이어야 한다. YAML 파싱 실패 시 즉시 거부.

**5.1.2 Zod 스키마 검증**

최상위 필드 및 각 노드 타입별 Zod 스키마를 통과해야 한다.

- `adplVersion`: 정수, 1 이상
- `name`: 정규식 `/^[a-z0-9][a-z0-9\-]{0,62}$/`
- `pipeline`: 배열, 최소 1개 항목
- 각 노드의 `type` 별 필수 필드 존재 확인

**5.1.3 참조 검증**

- `$nodes.X` 에서 `X` 가 동일 파이프라인 내에 존재해야 함
- `goto: X` 에서 `X` 가 동일 파이프라인 내에 존재해야 함
- `dependsOn: [X]` 에서 `X` 가 존재해야 함

**5.1.4 순서 제약 (Forward reference 금지)**

`$nodes.X` 는 현재 노드보다 **앞에 정의된 노드**만 참조 가능. 역방향 참조는 compile time 에러.

```yaml
# ❌ compile time error: 'implement' 는 'plan' 보다 뒤에 정의됨
- id: plan
  type: agent
  prompt: "${$nodes.implement.output.data}"  # 아직 실행 안 된 노드 참조

- id: implement
  type: agent
  prompt: "..."
```

**5.1.5 Cycle 감지**

`dependsOn` 관계에서 순환 의존이 있으면 거부.

**5.1.6 Node ID 유일성**

동일 파이프라인 내 `id` 는 unique 해야 함. 중첩 파이프라인(loop, branch 내부)의 노드 ID 도 전체 파이프라인 내에서 unique 를 권장하며, 충돌 시 경고를 발행한다.

**5.1.7 Shell 노드 검증**

`shell` 노드의 `command` 가 프로젝트 설정의 `allowlist` 에 있는지, `denylist` 에 없는지 확인. 미설정 시 경고만 출력하고 허용한다.

### 5.2 런타임 검증 (Run time)

파이프라인 실행 중 수행하는 동적 검증.

**에러 분류 체계**:

| 분류 | 코드 | 설명 | 재시도 가능 |
|------|------|------|------------|
| `transient` | `ERR_TRANSIENT` | 일시적 실패 (네트워크, rate limit) | 예 |
| `persistent` | `ERR_PERSISTENT` | 영구적 실패 (잘못된 입력, 권한 없음) | 아니오 |
| `quality` | `ERR_QUALITY` | 품질 기준 미달 (LLM 응답 schema 불일치) | 예 |
| `cost_limit` | `ERR_COST_LIMIT` | `totalCostLimit` 초과 | 아니오 |
| `cancellation` | `ERR_CANCELLED` | 사용자 또는 시스템에 의한 취소 | 아니오 |
| `policy_violation` | `ERR_POLICY` | 보안 정책 위반 (allowlist/denylist) | 아니오 |
| `timeout` | `ERR_TIMEOUT` | 타임아웃 초과 | 예 (설정에 따라) |

**타임아웃**:

- 노드 단위: `settings.nodeTimeout` 또는 노드의 `timeout` 필드 (초)
- 파이프라인 전체: `settings.totalTimeout` (초)
- 타임아웃 시 노드 상태 → `failure`, 에러 코드 `ERR_TIMEOUT`

### 5.3 에러 전파 규칙

**노드 레벨 `onFailure` 정책** (파이프라인 `settings.onNodeFailure` 를 override):

| 값 | 동작 |
|----|------|
| `"abort"` | 파이프라인 즉시 중단 |
| `"continue"` | 현재 노드를 `skipped` 상태로 표시, 후속 노드 계속 |
| `"retry"` | 노드의 `retryPolicy` 에 따라 재시도, 모두 실패 시 `abort` |

**우선순위**: 노드 `onFailure` > 파이프라인 `settings.onNodeFailure`

**Flow 노드 집계 규칙**:

| Flow 타입 | 실패 조건 | 설정으로 변경 가능 |
|-----------|-----------|-------------------|
| `branch` | 선택된 브랜치 내 노드 실패 = branch 노드 실패 | — |
| `parallel` | 하나라도 실패 시 (기본값) | `failFast: false` 설정 시 모두 완료 후 집계 |
| `loop` | 하나라도 실패 시 (기본값) | `continueOnError: true` 설정 시 계속 |
| `gate` | `rejected` 상태 = gate 노드 실패 | — |

### 5.4 에러 메시지 포맷

모든 ADPL 에러는 다음 구조를 따른다:

```typescript
interface AdplError {
  code: string;         // 에러 코드 (예: "ERR_REFERENCE")
  category: string;     // 에러 분류 (예: "compile_time")
  location: {
    nodeId?: string;    // 에러 발생 노드 ID
    field?: string;     // 에러 발생 필드 경로 (예: "when.field")
    line?: number;      // YAML 내 줄 번호 (가능한 경우)
  };
  message: string;      // 사람이 읽을 수 있는 에러 메시지
  suggestion?: string;  // 수정 제안 (typo 감지 등)
}
```

**에러 메시지 예시**:

```

  제안: 'implement' 를 'plan' 보다 앞에 정의하거나, 표현식을 제거하세요.

[ERR_UNKNOWN_NODE] 존재하지 않는 노드 'analyse' 를 참조합니다.
```

## 6. 버전 호환성

### 6.1 adplVersion 필드

ADPL 은 Semantic Versioning 을 따르며, `adplVersion` 필드는 Major 버전을 지정한다.

| 버전 구성 | 의미 |
|-----------|------|
| **Major** (`X.0.0`) | 하위 호환 불가 변경. `adplVersion` 값 증가. |
| **Minor** (`1.X.0`) | 하위 호환 추가. `adplVersion` 값 유지. |
| **Patch** (`1.0.X`) | 버그 수정. 사용자 파일 변경 불필요. |

`adplVersion: 1` 파일은 ADPL 1.x.x 의 모든 Minor/Patch 버전 엔진에서 동작한다.

### 6.2 Minor vs Major 변경 정의

**Minor 변경** (하위 호환, `adplVersion` 유지):

- 새 노드 타입 추가 (예: `mcp`, `gate`)
- 기존 노드에 선택적 필드 추가
- 새 필터/연산자 추가
- 새 컨텍스트 변수 추가
- 성능 개선

**Major 변경** (하위 호환 불가, `adplVersion` 증가):

- 필수 필드 추가 또는 기존 필드 삭제
- 필드 이름 변경 (rename)
- 기본값 변경 (동작 변화를 초래하는 경우)
- 연산자 의미 변경
- 컨텍스트 변수 구조 변경

### 6.3 마이그레이션 정책

**자동 마이그레이션 (Minor)**:

Minor 변경에서 새 필드의 기본값이 이전 동작과 동일하도록 설계한다. 기존 파이프라인 파일은 수정 없이 새 엔진에서 동작한다.

**수동 마이그레이션 (Major)**:

Major 버전 업그레이드 시:
1. 엔진이 `adplVersion` 불일치를 감지하고 에러 반환
2. 마이그레이션 가이드 문서 제공
3. (v1.5 예정) `autodev pipeline migrate --from 1 --to 2` CLI 명령으로 자동 변환

### 6.4 Deprecation 3단계

| 단계 | 기간 | 동작 |
|------|------|------|
| **Phase 1: Deprecated** | Minor 1개 이상 | 기능 동작하되 경고 로그 출력 |
| **Phase 2: Legacy** | Minor 1개 이상 | 기능 동작하되 UI 경고 + migration 강력 권고 |
| **Phase 3: Removed** | Major 버전 | 기능 제거, 실행 시 에러 |

Deprecated 기능은 최소 2개의 Minor 버전 동안 유지된다. Phase 3 제거는 반드시 Major 버전 업그레이드와 함께 이루어진다.

### 6.5 현재 버전: v1.0

| 항목 | 값 |
|------|-----|
| **스펙 버전** | 1.0.0 |
| **발행일** | 2026-04-19 |
| **상태** | 공식 (Stable) |
| **`adplVersion` 값** | `1` |

**v1.0 정책**:

- v1.x 기간 동안 Major 변경 없음 (최소 1년, v1.x 완료 후 검토)
- Minor 추가는 분기별 검토 후 발행
- 모든 Breaking change 는 v2.0 으로 집적

## 7. `agent` 노드

`agent` 노드는 LLM 에이전트를 호출하는 ADPL 의 핵심 노드다. AutoDev 의 Planner, Coder, Verifier 등 역할 기반 실행을 추상화하며, 다양한 AI 모델 백엔드를 통일된 인터페이스로 사용할 수 있다.

`agent` 노드는 프롬프트를 받아 LLM 에 전달하고, 응답을 `output.data` 로 반환한다. `output.schema` 를 정의하면 응답을 구조화된 JSON 으로 파싱하여 후속 노드에서 필드 단위로 참조할 수 있다. 재시도, 비용 제한, 모델 폴백 등 실무 요구사항을 노드 단위로 선언한다.

### 7.1 최소 예시

```yaml
- id: plan
  type: agent
  role: planner
  prompt: "다음 요청의 구현 계획을 수립해주세요: ${$task.prompt}"
```

### 7.2 스키마

| 필드 | 타입 | 필수 | 기본값 | 설명 |
|------|------|------|--------|------|
| `id` | `string` | 예 | — | 파이프라인 내 unique 식별자 |
| `type` | `"agent"` | 예 | — | 노드 타입 리터럴 |
| `role` | `RoleEnum` | 아니오 | `"planner"` | 에이전트 역할 (`planner` \| `coder` \| `verifier` \| `reviewer` \| `custom`) |
| `model` | `string` | 아니오 | 역할별 기본값 | 사용할 모델 ID |
| `prompt` | `string` | 조건부 † | — | 사용자 프롬프트 (Slot 1 표현식 사용 가능) |
| `systemPrompt` | `string` | 아니오 | 역할별 기본값 | 시스템 프롬프트 (role 이 없을 때만 권장) |
| `inputs` | `object` | 아니오 | `{}` | 추가 컨텍스트 주입 (`{ key: expression }`) |
| `output` | `OutputSpec` | 아니오 | — | 응답 스키마 및 파싱 설정 |
| `useMemory` | `boolean` | 아니오 | `false` | G3 persistent memory 활성화 |
| `maxTokens` | `integer` | 아니오 | 모델 기본값 | 최대 출력 토큰 수 |
| `temperature` | `number` | 아니오 | 역할별 기본값 | 샘플링 온도 (0–2) |
| `costLimit` | `number` | 아니오 | `null` | 이 노드 단독 비용 한도 (USD) |
| `timeout` | `integer` | 아니오 | `settings.nodeTimeout` | 타임아웃 (초) |
| `retryPolicy` | `RetryPolicy` | 아니오 | `null` | 재시도 설정 ([§2.6](#26-settings) 참조) |
| `fallback` | `FallbackSpec` | 아니오 | `null` | 실패 시 대체 모델 설정 |
| `toolPolicy` | `ToolPolicySpec` | 아니오 | 역할별 기본값 | 에이전트가 사용할 수 있는 도구 정책 |
| `when` | `Condition` | 아니오 | 항상 실행 | 실행 조건 ([§4.2](#42-slot-2-구조화-조건-structured-conditions) 참조) |
| `onFailure` | `FailurePolicy` | 아니오 | 파이프라인 상속 | 실패 시 정책 |

> † `prompt` 는 `role: custom` 일 때만 필수. `planner`, `coder`, `verifier`, `reviewer` 는 내장 프롬프트가 자동 주입되므로 생략 가능. `role: custom` 일 때는 `model` 도 함께 필수.

`OutputSpec` 스키마:

```yaml
output:
  schema:              # 기대 응답 구조 (Zod-compatible JSON Schema)
    score: number
    issues: array
    summary: string
  parseAs: json        # auto | json | text (기본값: auto)
  strict: false        # true 이면 schema 불일치 시 ERR_QUALITY 발생
```

`FallbackSpec` 스키마:

```yaml
fallback:
  model: gemini-cli           # 대체 모델
  onErrors: [ERR_TRANSIENT]   # 이 에러 코드에서만 폴백 (기본: 모든 에러)
  maxAttempts: 1              # 폴백 모델 시도 횟수
```

### 7.3 주요 필드 상세

#### `role`

에이전트의 역할을 선언한다. 역할에 따라 기본 모델, 시스템 프롬프트, 도구 정책이 자동으로 설정된다. **기본값은 `planner`** — Legacy AutoDev 의 주 패턴(Planning → Coding → Verify)에서 첫 노드로 가장 흔히 사용되기 때문이다.

| role | 기본 모델 | 기본 동작 | `prompt` 필수 |
|------|-----------|-----------|:---:|
| `planner` *(기본값)* | `claude-code` | 분석·계획 수립 프롬프트. 파일 읽기 도구 허용. | 아니오 |
| `coder` | `claude-code` | 코드 작성·수정 프롬프트. 파일 읽기·쓰기·실행 도구 허용. | 아니오 |
| `verifier` | `gemini-cli` | 결과 검증 프롬프트. 읽기 전용. 교차 검증을 위해 기본 모델이 coder 와 다름. | 아니오 |
| `reviewer` | `claude-code` | 코드 리뷰 프롬프트. 읽기 전용. | 아니오 |
| `custom` | **필수 지정** | 내장 프롬프트 없음. `prompt` 와 `model` 모두 명시 필요. | **예** |

#### `model`

사용할 LLM 모델 백엔드를 지정한다.

| 모델 ID | 백엔드 | 특징 | 비용 (입력/출력 per M tokens) |
|---------|--------|------|-------------------------------|
| `claude-code` | Anthropic Claude Code CLI | 파일 시스템 접근, 대형 컨텍스트 | ~$3 / $15 |
| `gemini-cli` | Google Gemini CLI | 1M 토큰 컨텍스트, 교차 검증용 | ~$1.25 / $5 |
| `codex-cli` | OpenAI Codex CLI | 빠른 코드 생성 | ~$2 / $8 |
| `api:claude-opus-4` | Anthropic API 직접 호출 | 최고 품질, 높은 비용 | ~$15 / $75 |
| `api:gpt-5` | OpenAI API | 다목적 | ~$10 / $30 |
| `api:gemini-2-flash` | Google API | 빠른 응답, 저비용 | ~$0.075 / $0.30 |

`api:` 접두사는 CLI 가 아닌 API 직접 호출을 의미한다. CLI 모델은 별도 프로세스를 실행하여 파일 시스템 도구를 포함한 전체 에이전트 기능을 활용한다.

#### `inputs`

후속 노드의 결과나 외부 값을 에이전트 컨텍스트에 주입한다. Slot 1 표현식을 값으로 사용한다.

```yaml
inputs:
  planResult: "${$nodes.plan.output.data}"         # 이전 노드 전체 출력
  codeScore: "${$nodes.review.output.data.score}"  # 특정 필드만 추출
  taskId: "${$task.id}"                            # 컨텍스트 변수
```

주입된 값은 시스템 프롬프트에 `{{inputs.planResult}}` 형태로 포함되거나, `prompt` 의 `${inputs.planResult}` 보간으로 참조한다.

> ⚠️ `inputs` 에 `$nodes.X.output` 전체를 넣지 말고, 필요한 하위 필드만 추출하여 주입하라. 불필요한 토큰 소비를 줄이고 에이전트 컨텍스트 오염을 방지한다.

#### `useMemory`

`true` 이면 AutoDev G3 persistent memory 를 이 에이전트 세션에 활성화한다. 이전 Task 에서 축적한 프로젝트 컨텍스트(코드 구조, 결정 사항 등)가 시스템 프롬프트에 자동으로 포함된다. 기본값 `false` — 메모리 비용과 토큰 사용을 고려하여 필요한 노드에만 활성화한다.

#### `retryPolicy` + `fallback`

실패 시 세 가지 전략을 조합할 수 있다:

| 전략 | 설정 | 동작 |
|------|------|------|
| **같은 모델 재시도** | `retryPolicy.maxAttempts: 3` | 동일 모델로 최대 3회 재시도 |
| **폴백 모델 전환** | `fallback.model: gemini-cli` | 재시도 소진 후 다른 모델로 전환 |
| **즉시 실패** | `onFailure: abort` | 재시도 없이 파이프라인 중단 |

`ERR_COST_LIMIT` 에러는 재시도 대상에서 자동으로 제외된다 — 비용 한도를 초과한 경우 재시도해도 동일하게 실패하기 때문이다.

### 7.4 실전 예시

**예시 1: Legacy-equivalent Plan → Code → Verify 체인**

기존 AutoDev Task 의 단일 실행 파이프라인을 ADPL 로 재현한다.

```yaml
adplVersion: 1
name: plan-code-verify
description: 기존 AutoDev 파이프라인과 동등한 3단계 실행

        estimatedFiles: array
      strict: false

    type: agent

      구현 결과를 검증해주세요.
```

**예시 3: Fallback + Retry 조합 (Rate limit 대응)**

```yaml
- id: analyze
  type: agent
  role: planner
  model: claude-code
```

### 7.5 에러 처리

| 에러 코드 | 분류 | 원인 | 재시도 | 기본 동작 |
|-----------|------|------|--------|-----------|
| `ERR_TRANSIENT` | transient | Rate limit, 네트워크 오류, 모델 서비스 불안정 | 예 | retryPolicy 에 따라 재시도 |
| `ERR_QUALITY` | quality | `output.strict: true` 인데 schema 불일치 | 예 | 재시도 후 실패 |
| `ERR_COST_LIMIT` | cost_limit | 노드 `costLimit` 또는 파이프라인 `totalCostLimit` 초과 | **아니오** | 즉시 실패 |
| `ERR_TIMEOUT` | timeout | 노드 `timeout` 초과 | 설정에 따라 | onFailure 정책 적용 |
| `ERR_PERSISTENT` | persistent | 잘못된 모델 ID, 인증 실패, 잘못된 schema | 아니오 | 즉시 실패 |
| `ERR_POLICY` | policy_violation | 허용되지 않은 도구 사용 시도 | 아니오 | 즉시 실패 |

**에러 분류 흐름**:

```
에이전트 실행 실패
  ├─ HTTP 429 / 503 → ERR_TRANSIENT → retryPolicy 적용
  ├─ 비용 초과 → ERR_COST_LIMIT → 즉시 abort (retry 금지)
  ├─ schema 불일치 + strict: true → ERR_QUALITY → retryPolicy 적용
  ├─ HTTP 401 / 잘못된 모델 → ERR_PERSISTENT → 즉시 abort
  └─ timeout 초과 → ERR_TIMEOUT → onFailure 정책 적용
```

### 7.6 Anti-patterns

```yaml
# ❌ role 이 있는데 systemPrompt 를 따로 지정 — role 이 systemPrompt 를 덮어씀
- id: plan
  type: agent
  role: planner
  systemPrompt: "당신은 계획가입니다."  # planner role 의 기본 프롬프트와 충돌

# ✅ custom role 을 쓰거나 systemPrompt 생략
- id: plan
  type: agent
  role: planner
  prompt: "추가 지시: 반드시 5단계 이하로 계획하세요."
```

```yaml
# ❌ inputs 에 output 전체 주입 — 불필요한 토큰 낭비
inputs:
  data: "${$nodes.analyze.output}"    # status, duration, costUsd 등 불필요한 필드 포함

# ✅ 필요한 필드만 추출
inputs:
  data: "${$nodes.analyze.output.data}"
  score: "${$nodes.analyze.output.data.score}"
```

```yaml
# ❌ retryPolicy.maxAttempts 너무 높음 — 비용 폭발 위험
retryPolicy:
  maxAttempts: 10  # agent 노드는 3 이하 권장

# ✅ 적절한 횟수 + fallback 조합
retryPolicy:
  maxAttempts: 2
fallback:
  model: gemini-cli
```

## 8. `shell` 노드

`shell` 노드는 셸 명령을 실행하고 출력을 캡처한다. 빌드, 테스트, 린트, git 작업 등 CLI 기반 검증 단계에 사용된다. 실행 환경은 Task 의 worktree 경로가 기본 `cwd` 로 설정되며, 환경 변수는 명시적으로 주입해야 한다.

`shell` 노드의 출력(`stdout`, `stderr`, `exitCode`)은 `$nodes.<id>.output.data` 를 통해 후속 노드에서 참조할 수 있다. `outputFormat: json` 으로 설정하면 stdout 을 자동 파싱하여 구조화된 데이터로 접근한다.

### 8.1 최소 예시

```yaml
- id: test
  type: shell
  command: "pnpm test"
```

### 8.2 스키마

| 필드 | 타입 | 필수 | 기본값 | 설명 |
|------|------|------|--------|------|
| `id` | `string` | 예 | — | 파이프라인 내 unique 식별자 |
| `type` | `"shell"` | 예 | — | 노드 타입 리터럴 |
| `command` | `string` | 예* | — | 실행할 명령 (Slot 1 표현식 사용 가능) |
| `args` | `string[]` | 아니오 | `[]` | `exec` 모드에서 명령 인자 배열 |
| `mode` | `"shell" \| "exec"` | 아니오 | `"shell"` | 실행 방식 |
| `cwd` | `string` | 아니오 | worktree 루트 | 작업 디렉토리 (Slot 1 표현식 가능) |
| `env` | `object` | 아니오 | `{}` | 추가 환경 변수 (Slot 1 표현식 가능) |
| `stdin` | `string` | 아니오 | `null` | 표준 입력 (Slot 1 표현식 가능) |
| `outputFormat` | `"auto" \| "text" \| "json" \| "lines" \| "binary"` | 아니오 | `"auto"` | stdout 파싱 방식 |
| `failOnNonZero` | `boolean` | 아니오 | `true` | exit code ≠ 0 이면 노드 실패 처리 |
| `allowExitCodes` | `integer[]` | 아니오 | `[]` | 실패로 처리하지 않을 추가 exit code 목록 |
| `timeout` | `integer` | 아니오 | `settings.nodeTimeout` | 타임아웃 (초) |
| `retryPolicy` | `RetryPolicy` | 아니오 | `null` | 재시도 설정 |
| `idempotencyKey` | `string` | 아니오 | `null` | 멱등성 키 (재시도 중복 방지) |
| `when` | `Condition` | 아니오 | 항상 실행 | 실행 조건 |
| `onFailure` | `FailurePolicy` | 아니오 | 파이프라인 상속 | 실패 시 정책 |

### 8.3 주요 필드 상세

#### `mode`: shell vs exec

| 모드 | 동작 | 보안 | 사용 시기 |
|------|------|------|-----------|
| `shell` | `sh -c "<command>"` 로 실행. 파이프, 리다이렉트, 글로브 등 셸 기능 사용 가능. | 셸 인젝션 위험 — command 에 외부 입력 포함 시 주의 | 대부분의 경우 |
| `exec` | 명령을 직접 `execve` 로 실행. `args` 배열 필수. 셸 기능 없음. | 인젝션 위험 없음 | 외부 입력을 `args` 에 안전하게 전달할 때 |

```yaml
# shell 모드 (기본) — 파이프 사용 가능
- id: count-errors
  type: shell
  mode: shell
  command: "pnpm build 2>&1 | grep -c 'error'"

# exec 모드 — 인자가 사용자 입력인 경우
- id: grep-safe
  type: shell
  mode: exec
  command: "grep"
  args: ["-r", "${$task.config.searchTerm}", "./src"]
```

#### `outputFormat`

| 값 | 동작 | `output.data.parsed` 타입 |
|----|------|---------------------------|
| `auto` | stdout 이 유효한 JSON 이면 파싱, 아니면 text | `object` 또는 `string` |
| `text` | 그대로 문자열 반환 | `string` |
| `json` | JSON 파싱 강제 (실패 시 `ERR_QUALITY`) | `object` |
| `lines` | 줄 단위 배열로 반환 | `string[]` |
| `binary` | Base64 인코딩 문자열 반환 | `string` |

`output.data` 구조:

```typescript
{
  stdout: string,       // 원본 stdout
  stderr: string,       // 원본 stderr
  exitCode: number,     // 프로세스 exit code
  parsed?: unknown      // outputFormat 파싱 결과 (auto/json/lines 시)
}
```

#### `stdin` 주입

긴 텍스트를 명령에 전달할 때 `stdin` 을 사용한다. Codex CLI 처럼 stdin 으로 프롬프트를 받는 도구에 유용하다:

```yaml
- id: codex-run
  type: shell
  command: "codex"
  stdin: "${$nodes.plan.output.data.prompt}"
  outputFormat: text
```

```yaml
- id: test

  failOnNonZero: false
```

### 8.5 에러 처리

| 상황 | 에러 코드 | 동작 |
|------|-----------|------|
| exit code ≠ 0 (`failOnNonZero: true`) | `ERR_PERSISTENT` | onFailure 정책 적용 |
| `allowExitCodes` 에 포함된 exit code | — | 성공으로 처리 |
| 타임아웃 | `ERR_TIMEOUT` | SIGTERM 후 5초 대기, 이후 SIGKILL |
| `outputFormat: json` 인데 유효하지 않은 JSON | `ERR_QUALITY` | retryPolicy 적용 |
| `allowlist` 에 없는 명령 | `ERR_POLICY` | 즉시 실패, 실행 안 함 |

**타임아웃 종료 순서**:

1. 타임아웃 도달 → `SIGTERM` 전송
2. 5초 대기 (graceful shutdown)
3. 여전히 실행 중이면 `SIGKILL` 강제 종료
4. `stderr` 에 타임아웃 메시지 포함하여 `ERR_TIMEOUT` 반환

**stderr 수집**: stderr 는 항상 캡처하여 `output.data.stderr` 로 반환한다. `failOnNonZero: false` 라도 stderr 는 기록된다.

### 8.6 Anti-patterns

```yaml
# ❌ command 에 사용자 입력 직접 포함 — 셸 인젝션 위험
command: "grep -r ${$task.config.searchTerm} ./src"

# ✅ exec 모드로 안전하게 전달
mode: exec
command: "grep"
args: ["-r", "${$task.config.searchTerm}", "./src"]
```

```yaml
# ❌ outputFormat: json 인데 stdout 에 non-JSON 출력
command: "pnpm test && echo 'done'"  # 'done' 문자열 때문에 JSON 파싱 실패

# ✅ JSON 만 출력하는 명령 사용 또는 auto 모드
outputFormat: auto
```

```yaml
# ❌ 환경 변수 값을 command 에 inline 주입
command: "curl -H 'Authorization: Bearer ${$env.TOKEN}' ..."

# ✅ env 필드로 주입
command: "curl -H 'Authorization: Bearer $MY_TOKEN' ..."
env:
  MY_TOKEN: "${$env.TOKEN}"
```

> 상세 설계: [설계 4B4](../design-docs/19_PhaseP_design4b4_actions.md)

## 9. `http` 노드

`http` 노드는 HTTP/HTTPS 요청을 보내고 응답을 캡처한다. 외부 API 호출, 상태 업데이트, 데이터 조회 등에 사용한다. Idempotent 재시도, `Retry-After` 헤더 자동 처리, 응답 스키마 검증 기능을 내장한다.

요청 URL, 헤더, body 에 Slot 1 표현식을 사용할 수 있어 이전 노드 결과를 동적으로 포함할 수 있다.

### 9.1 최소 예시

```yaml
- id: fetch-issues
  type: http
  url: "https://api.github.com/repos/${$project.name}/issues"
  method: GET
  headers:
    Authorization: "Bearer ${$env.GITHUB_TOKEN}"
```

### 9.2 스키마

| 필드 | 타입 | 필수 | 기본값 | 설명 |
|------|------|------|--------|------|
| `id` | `string` | 예 | — | 파이프라인 내 unique 식별자 |
| `type` | `"http"` | 예 | — | 노드 타입 리터럴 |
| `url` | `string` | 예 | — | 요청 URL (Slot 1 표현식 가능) |
| `method` | `HttpMethod` | 아니오 | `"GET"` | HTTP 메서드 |
| `headers` | `object` | 아니오 | `{}` | 요청 헤더 (값에 Slot 1 표현식 가능) |
| `queryParams` | `object` | 아니오 | `{}` | 쿼리 파라미터 (자동 URL 인코딩) |
| `bodyFormat` | `BodyFormat` | 아니오 | `"json"` | 요청 body 포맷 |
| `body` | `any` | 아니오 | `null` | 요청 body (Slot 1 표현식 가능) |
| `allowedHosts` | `string[]` | 아니오 | 프로젝트 설정 상속 | 허용 호스트 목록 (보안 정책) |
| `idempotencyKey` | `string` | 아니오 | `null` | 멱등성 키 (Slot 1 표현식 가능) |
| `timeout` | `integer` | 아니오 | `settings.nodeTimeout` | 타임아웃 (초) |
| `retryPolicy` | `RetryPolicy` | 아니오 | 메서드별 기본값 | 재시도 설정 |
| `when` | `Condition` | 아니오 | 항상 실행 | 실행 조건 |
| `onFailure` | `FailurePolicy` | 아니오 | 파이프라인 상속 | 실패 시 정책 |

`HttpMethod` 허용 값: `GET` | `POST` | `PUT` | `PATCH` | `DELETE` | `HEAD` | `OPTIONS`

`BodyFormat` 허용 값:

| 값 | `Content-Type` 자동 설정 | 설명 |
|----|--------------------------|------|
| `json` | `application/json` | body 를 JSON 직렬화 |
| `form` | `application/x-www-form-urlencoded` | key=value 인코딩 |
| `text` | `text/plain` | body 를 그대로 문자열 전송 |
| `binary` | `application/octet-stream` | Base64 디코딩 후 전송 |
| `multipart` | `multipart/form-data` | 파일 업로드 |

### 9.3 주요 필드 상세

#### 메서드별 Idempotent 재시도 기본값

| 메서드 | 기본 retry | 이유 |
|--------|------------|------|
| `GET`, `HEAD`, `OPTIONS` | 3회, exponential backoff | 멱등 메서드 — 재시도 안전 |
| `PUT`, `DELETE` | 3회, exponential backoff | 멱등 메서드 |
| `POST`, `PATCH` | **0회** (재시도 없음) | 비멱등 — 중복 요청 위험 |
| `POST` + `idempotencyKey` | 3회 | 키로 중복 방지 가능 |

#### `retryPolicy.onStatuses`

재시도할 HTTP 상태 코드 목록. 기본값:

```yaml
retryPolicy:
  onStatuses: [429, 502, 503, 504]
```

429 응답에 `Retry-After` 헤더가 있으면 헤더 값을 대기 시간으로 자동 사용 (`retryPolicy.initialDelay` 무시).

#### `output.data` 구조

```typescript
{
  status: number,      // HTTP 상태 코드
  headers: object,     // 응답 헤더 (소문자 키)
  body: unknown        // 응답 body (Content-Type 에 따라 자동 파싱)
}
```

응답 `Content-Type` 이 `application/json` 이면 body 가 자동으로 객체로 파싱된다.

### 9.4 실전 예시

**예시 1: GitHub API PR 조회**

```yaml
- id: fetch-prs
  type: http
  url: "https://api.github.com/repos/${$project.name}/pulls"
  method: GET
  headers:
    Authorization: "Bearer ${$env.GITHUB_TOKEN}"
    Accept: "application/vnd.github.v3+json"
  queryParams:
    state: open
    per_page: "10"
  retryPolicy:
    maxAttempts: 3
    backoff: exponential
    initialDelay: 5
    onStatuses: [429, 502, 503]
```

**예시 2: Slack webhook POST (idempotencyKey 포함)**

```yaml
- id: slack-notify
  type: http
  url: "${$env.SLACK_WEBHOOK_URL}"
  method: POST
  bodyFormat: json
  body:
    text: "Task ${$task.id} 완료 ✅"
    username: "AutoDev Bot"
  idempotencyKey: "task-${$task.id}-slack-notify"
  retryPolicy:
    maxAttempts: 2
    backoff: fixed
    initialDelay: 5
    onStatuses: [429, 500, 502, 503]
```

**예시 3: 파일 업로드 (multipart)**

```yaml
- id: upload-report
  type: http
  url: "https://storage.example.com/upload"
  method: POST
  bodyFormat: multipart
  headers:
    Authorization: "Bearer ${$env.STORAGE_TOKEN}"
  body:
    file:
      content: "${$nodes.generate-report.output.data}"
      filename: "report-${$task.id}.json"
      contentType: "application/json"
    metadata:
      taskId: "${$task.id}"
```

### 9.5 에러 처리

| 상황 | 에러 코드 | 분류 | 재시도 |
|------|-----------|------|--------|
| 네트워크 오류 (`ENOTFOUND`, `ECONNRESET`) | `ERR_TRANSIENT` | transient | 예 |
| 401 Unauthorized | `ERR_PERSISTENT` | persistent | 아니오 |
| 403 Forbidden | `ERR_PERSISTENT` | persistent | 아니오 |
| 404 Not Found | `ERR_PERSISTENT` | persistent | 아니오 |
| 429 Too Many Requests | `ERR_TRANSIENT` | transient | 예 (`Retry-After` 자동 적용) |
| 5xx Server Error | `ERR_TRANSIENT` | transient | 예 |
| 타임아웃 | `ERR_TIMEOUT` | timeout | 설정에 따라 |
| 허용되지 않은 호스트 | `ERR_POLICY` | policy_violation | 아니오 |

### 9.6 Anti-patterns

```yaml
# ❌ allowedHosts 없이 동적 URL — 임의 호스트로 요청 가능
url: "${$task.config.targetUrl}"  # 악의적인 내부 URL 요청 위험

# ✅ 허용 호스트 명시
allowedHosts: ["api.github.com", "hooks.slack.com"]
url: "${$task.config.targetUrl}"  # 위 목록 외 호스트는 ERR_POLICY
```

```yaml
# ❌ POST 에 idempotencyKey 없이 retry 설정 — 중복 요청 발생
- id: create-issue
  type: http
  method: POST
  retryPolicy:
    maxAttempts: 3  # POST 가 여러 번 실행될 수 있음

# ✅ idempotencyKey 추가
idempotencyKey: "create-issue-${$task.id}"
```

```yaml
# ❌ body 에 secret 직접 포함
body:
  api_key: "sk-prod-abc123"  # 로그에 노출 위험

# ✅ $env 로 주입 (로그에서 자동 마스킹)
headers:
  Authorization: "Bearer ${$env.API_KEY}"
```

> 상세 설계: [설계 4B4](../design-docs/19_PhaseP_design4b4_actions.md)

## 10. `webhook_out` 노드

`webhook_out` 노드는 Slack, Discord, Microsoft Teams, 또는 임의 HTTP 엔드포인트로 알림을 발송한다. `http` 노드의 특수 케이스로, provider 별 body 템플릿과 rate limit 처리를 내장한다.

알림 실패가 파이프라인 전체를 중단해서는 안 되는 경우가 대부분이므로, 기본적으로 `silentFail: true` 로 설정된다. 파이프라인 로직의 일부가 아닌 부가적인 알림에만 사용하라 — 알림 결과에 따라 분기가 필요하다면 `http` 노드를 사용하라.

### 10.1 최소 예시

```yaml
- id: notify-success
  type: webhook_out
  provider: slack
  url: "${$env.SLACK_WEBHOOK_URL}"
  body:
    text: "Task ${$task.id} 완료 ✅"
```

### 10.2 스키마

| 필드 | 타입 | 필수 | 기본값 | 설명 |
|------|------|------|--------|------|
| `id` | `string` | 예 | — | 파이프라인 내 unique 식별자 |
| `type` | `"webhook_out"` | 예 | — | 노드 타입 리터럴 |
| `provider` | `ProviderEnum` | 아니오 | `"generic"` | 대상 플랫폼 (`slack` \| `discord` \| `teams` \| `generic`) |
| `url` | `string` | 예 | — | Webhook URL (Slot 1 표현식 가능) |
| `body` | `object` | 예 | — | 발송할 payload (provider 별 스키마) |
| `when` | `Condition` | 아니오 | 항상 실행 | 발송 조건 (Slot 2 표현식) |
| `silentFail` | `boolean` | 아니오 | `true` | 실패 시 파이프라인 계속 실행 |
| `failOnError` | `boolean` | 아니오 | `false` | true 이면 실패 시 파이프라인 중단 |
| `rateLimitPerMinute` | `integer` | 아니오 | provider 기본값 | 분당 최대 발송 수 |
| `timeout` | `integer` | 아니오 | `30` | 타임아웃 (초, 기본값 짧게 설정) |
| `retryPolicy` | `RetryPolicy` | 아니오 | 1회 재시도 | 재시도 설정 |

### 10.3 주요 필드 상세

#### Provider 별 body 스키마

**`slack`**:
```yaml
body:
  text: "메시지 텍스트"              # 필수
  username: "AutoDev Bot"            # 선택: 발신자 이름
  icon_emoji: ":robot_face:"         # 선택: 아이콘
  attachments: []                    # 선택: 리치 첨부 (Slack Block Kit)
```

**`discord`**:
```yaml
body:
  content: "메시지 텍스트"           # 필수
  username: "AutoDev Bot"            # 선택
  embeds:                            # 선택: 임베드 카드
    - title: "Task 완료"
      description: "${$task.id}"
      color: 3066993
```

**`teams`**:
```yaml
body:
  "@type": "MessageCard"
  "@context": "https://schema.org/extensions"
  summary: "AutoDev 알림"
  themeColor: "0072C6"
  sections:
    - activityTitle: "Task 완료"
      activityText: "${$task.prompt | truncate(200)}"
```

**`generic`**:
```yaml
body:                                # 임의 JSON — 그대로 전송
  event: "task.complete"
  taskId: "${$task.id}"
  score: "${$nodes.verify.output.data.score}"
```

#### `when` 조건부 발송

특정 조건에서만 알림을 발송한다:

```yaml
- id: notify-failure
  type: webhook_out
  provider: slack
  url: "${$env.SLACK_WEBHOOK_URL}"
  when:
    field: $nodes.verify.output.data.passed
    eq: false
  body:
    text: "⚠️ 검증 실패: ${$nodes.verify.output.data.issues | json}"
```

#### Rate limit

`rateLimitPerMinute` 초과 시 초과분은 자동으로 스로틀되어 큐에 대기한다. Provider 기본값:

| Provider | 기본 rateLimitPerMinute |
|----------|------------------------|
| `slack` | 60 |
| `discord` | 30 |
| `teams` | 60 |
| `generic` | 100 |

### 10.4 실전 예시

**예시 1: Slack 성공 알림**

```yaml
- id: slack-success
  type: webhook_out
  provider: slack
  url: "${$env.SLACK_WEBHOOK_URL}"
  body:
    text: "✅ Task 완료"
    attachments:
      - color: good
        fields:
          - title: "Task ID"
            value: "${$task.id}"
            short: true
          - title: "비용"
            value: "${$nodes.code.output.costUsd | toFixed(4)} USD"
            short: true
```

**예시 2: Discord + 조건부 (실패만 알림)**

```yaml
- id: discord-alert
  type: webhook_out
  provider: discord
  url: "${$env.DISCORD_WEBHOOK_URL}"
  when: "$nodes.verify.output.data.score < 70"
  body:
    content: "🚨 검증 점수 미달"
    embeds:
      - title: "Task ${$task.id} 실패"
        description: "${$nodes.verify.output.data.issues | json | truncate(500)}"
        color: 15158332
  silentFail: false
  failOnError: false
```

**예시 3: Generic webhook (커스텀 JSON)**

```yaml
- id: custom-webhook
  type: webhook_out
  provider: generic
  url: "${$env.CUSTOM_WEBHOOK_URL}"
  body:
    event: "autodev.task.complete"
    timestamp: "${$trigger.firedAt}"
    task:
      id: "${$task.id}"
      prompt: "${$task.prompt | truncate(100)}"
    result:
      score: "${$nodes.verify.output.data.score}"
      passed: "${$nodes.verify.output.data.passed}"
```

### 10.5 에러 처리

`silentFail: true` (기본값) 일 때:
- 요청 실패 → **파이프라인 계속 실행**
- 경고 로그에 실패 사유 기록 (`WARN: webhook_out 'X' failed: ...`)
- `output.data.status` 는 `"failed"` 로 설정되나 노드 상태는 `"success"`

`failOnError: true` 설정 시:
- 실패 → 노드 상태 `"failure"` → `onFailure` 정책 적용
- 중요 알림(예: 감사 로그 시스템)에서 사용

### 10.6 Anti-patterns

```yaml
# ❌ webhook_out 으로 핵심 로직 결과를 전달 — 실패 시 무시됨
- id: notify-and-depend
  type: webhook_out
  provider: generic
  url: "${$env.APPROVAL_SYSTEM_URL}"
  # silentFail: true 가 기본값이므로 실패해도 파이프라인 계속 실행됨

# ✅ 핵심 로직에는 http 노드 + failOnError 사용
- id: submit-to-approval
  type: http
  url: "${$env.APPROVAL_SYSTEM_URL}"
  method: POST
  onFailure: abort
```

```yaml
# ❌ 루프 안에서 매 반복마다 알림 — rate limit 위험
- id: process-files
  type: loop
  items: "${$task.config.files}"
  pipeline:
    - id: notify-each
      type: webhook_out
      provider: slack     # 파일 100개 → 100번 발송 → rate limit 초과

# ✅ 루프 완료 후 한 번만 발송
- id: loop-end-notify
  type: webhook_out
  provider: slack
  body:
    text: "파일 ${length($task.config.files)} 개 처리 완료"
```

> 상세 설계: [설계 4B4](../design-docs/19_PhaseP_design4b4_actions.md)

## 11. `branch` 노드

`branch` 노드는 조건에 따라 실행 경로를 선택한다. `cases` 배열의 각 항목의 `when` 표현식을 순서대로 평가하고, 첫 번째로 매칭되는 case 의 하위 노드를 실행한다 (기본값 `evaluationMode: first_match`).

`if-elif-else` 구조에 대응한다. 복잡한 다중 분기, 점수 기반 라우팅, 태그 기반 에이전트 선택 등에 활용한다.

### 11.1 최소 예시

```yaml
- id: route-by-quality
  type: branch
  cases:
    - when:
        field: $nodes.verify.output.data.score
        gte: 80
      then:
        - id: approve
          type: agent
          role: custom
          model: claude-code
          prompt: "코드 품질이 양호합니다. 완료 메시지를 작성해주세요."
    - default: true
      then:
        - id: request-fix
          type: agent
          role: coder
          prompt: "품질 점수가 낮습니다. 개선해주세요."
```

### 11.2 스키마

| 필드 | 타입 | 필수 | 기본값 | 설명 |
|------|------|------|--------|------|
| `id` | `string` | 예 | — | 파이프라인 내 unique 식별자 |
| `type` | `"branch"` | 예 | — | 노드 타입 리터럴 |
| `cases` | `CaseSpec[]` | 예 | — | 분기 조건 목록 |
| `evaluationMode` | `"first_match" \| "all_match"` | 아니오 | `"first_match"` | 평가 방식 |
| `onMissingMatch` | `"skip" \| "error"` | 아니오 | `"skip"` | 매칭 case 없을 때 동작 |
| `when` | `Condition` | 아니오 | 항상 실행 | branch 노드 자체 실행 조건 |
| `onFailure` | `FailurePolicy` | 아니오 | 파이프라인 상속 | 실패 시 정책 |

`CaseSpec` 스키마:

| 필드 | 타입 | 필수 | 설명 |
|------|------|------|------|
| `when` | `Condition` | 예* | 매칭 조건 (Slot 2 표현식, [§4.2](#42-slot-2-구조화-조건-structured-conditions) 참조) |
| `default` | `boolean` | 예* | `true` 이면 다른 case 모두 불일치 시 선택 |
| `then` | `NodeSpec[]` | 예 | 이 case 가 선택됐을 때 실행할 노드 배열 |

> *`when` 또는 `default: true` 중 하나는 반드시 있어야 함. 둘 다 있으면 compile time error.

### 11.3 주요 필드 상세

#### `evaluationMode`

| 모드 | 동작 | 사용 시기 |
|------|------|-----------|
| `first_match` | cases 를 순서대로 평가, 첫 매칭 case 만 실행 후 중단 | if-elif-else 분기 |
| `all_match` | 매칭되는 모든 cases 실행 (병렬 아닌 순차 실행) | 여러 조건이 동시에 참일 때 각각 실행 |

`all_match` 는 `first_match` 와 달리 여러 case 가 선택될 수 있다. 예를 들어 Task 에 `ui` 태그와 `api` 태그가 모두 있을 때 UI 리뷰와 API 리뷰를 모두 실행하는 경우에 적합하다.

#### `default: true`

`first_match` 모드에서 `when` 이 없는 case — 다른 모든 case 가 불일치할 때 선택된다. else 분기. `cases` 배열의 마지막에 위치시키는 것을 권장한다 (앞에 위치하면 항상 선택되어 이후 case 가 평가되지 않음).

#### `onMissingMatch`

| 값 | 동작 |
|----|------|
| `"skip"` | 매칭 case 없으면 `branch` 노드를 `skipped` 상태로 완료. 파이프라인 계속. |
| `"error"` | 매칭 case 없으면 노드 실패 (`ERR_PERSISTENT`). `onFailure` 정책 적용. |

#### 하위 노드 실행

`then` 배열의 노드는 branch 노드 내부의 미니 파이프라인으로 실행된다. 이 노드들은:
- 상위 파이프라인의 `$nodes` 컨텍스트에 접근 가능
- `$flow.matchedBranch` 로 선택된 case 인덱스 접근 가능
- 실패 시 branch 노드 전체가 실패 처리

### 11.4 실전 예시

**예시 1: Tag 기반 에이전트 선택**

```yaml
- id: select-reviewer
  type: branch
  cases:
    - when:
        field: $task.tags
        contains: ui
      then:
        - id: ui-review
          type: agent
          role: custom
          model: claude-code
          systemPrompt: "당신은 UI/UX 전문가입니다."
          prompt: "UI 컴포넌트를 리뷰해주세요: ${$task.prompt}"
    - when:
        field: $task.tags
        contains: security
      then:
        - id: security-review
          type: agent
          role: custom
          model: api:claude-opus-4
          systemPrompt: "당신은 보안 전문가입니다."
          prompt: "보안 관점에서 코드를 검토해주세요: ${$task.prompt}"
    - default: true
      then:
        - id: standard-review
          type: agent
          role: reviewer
          prompt: "코드를 리뷰해주세요: ${$task.prompt}"
```

**예시 2: 점수 기반 3-way 분기**

```yaml
- id: grade-result
  type: branch
  cases:
    - when: "$nodes.verify.output.data.score >= 90"
      then:
        - id: ship
          type: shell
          command: "pnpm ship"
    - when: |
        $nodes.verify.output.data.score >= 70 and
        $nodes.verify.output.data.score < 90
      then:
        - id: manual-review
          type: agent
          role: reviewer
          prompt: "점수 ${$nodes.verify.output.data.score}점 — 추가 검토가 필요합니다."
    - default: true
      then:
        - id: rework
          type: agent
          role: coder
          prompt: |
            점수 ${$nodes.verify.output.data.score}점 — 재작업이 필요합니다.
            이슈: ${$nodes.verify.output.data.issues | json}
```

**예시 3: all_match — 다중 액션**

```yaml
- id: multi-action
  type: branch
  evaluationMode: all_match
  cases:
    - when:
        field: $task.tags
        contains: ui
      then:
        - id: ui-check
          type: agent
          role: reviewer
          prompt: "UI 접근성을 확인해주세요."
    - when:
        field: $task.tags
        contains: api
      then:
        - id: api-check
          type: agent
          role: reviewer
          prompt: "API 계약을 검토해주세요."
    - when:
        field: $task.config.requireDocs
        eq: true
      then:
        - id: doc-check
          type: agent
          role: reviewer
          prompt: "문서 업데이트 여부를 확인해주세요."
```

Task 에 `ui`, `api` 태그가 모두 있고 `requireDocs: true` 이면 세 case 모두 실행된다.

### 11.5 에러 처리

| 상황 | 에러 코드 | 동작 |
|------|-----------|------|
| `when` 평가 중 런타임 에러 | — | `false` 로 간주 (다음 case 평가) |
| `when` 에서 `ReferenceError` | `ERR_PERSISTENT` | 파이프라인 실패 (참조 에러는 진행 불가) |
| 매칭 case 없음 + `onMissingMatch: error` | `ERR_PERSISTENT` | 노드 실패 |
| `then` 내부 노드 실패 | 해당 노드 에러 코드 | branch 노드 실패로 전파 |

### 11.6 Anti-patterns

```yaml
# ❌ when 에서 JS 메서드 사용 — 지원 안 함
when: "$task.tags.includes('ui')"  # JavaScript 메서드

# ✅ ADPL 조건 연산자 사용 (§4.2 참조)
when:
  field: $task.tags
  contains: ui
```

```yaml
# ❌ default 없이 all cases 가 false 일 수 있는 상황 — 의도치 않은 skip
cases:
  - when: { field: $nodes.score, gte: 90 }
    then: [...]
  - when: { field: $nodes.score, gte: 80 }
    then: [...]
# score < 80 이면 아무것도 실행 안 됨 (onMissingMatch: skip 기본값)

# ✅ default 추가
  - default: true
    then:
      - id: low-score-handler
        type: agent
        ...
```

```yaml
# ❌ first_match 기대하며 all_match 설정 — 예상 외 다중 실행
evaluationMode: all_match
cases:
  - when: { field: $score, gte: 80 }  # score=95이면 이것도 매칭
    then: [...]
  - when: { field: $score, gte: 90 }  # score=95이면 이것도 매칭 → 둘 다 실행
    then: [...]
```

## 12. `parallel` 노드

`parallel` 노드는 여러 branch 를 동시에 실행하고 결과를 `mergeStrategy` 로 통합한다. 독립적인 작업(lint + test + typecheck, 다중 모델 검증 등)을 병렬로 처리하여 전체 실행 시간을 줄인다.

각 branch 는 독립 실행 단위이므로 branch 간 `$nodes` 참조는 할 수 없다. 병렬 실행 완료 후 `mergeStrategy` 에 따라 성공/실패를 판정하고, `output.data` 에 집계 결과를 반환한다.

### 12.1 최소 예시

```yaml
- id: checks
  type: parallel
  mergeStrategy: all_must_pass
  branches:
    - id: lint
      nodes:
        - id: lint-cmd
          type: shell
          command: "pnpm lint"
    - id: test
      nodes:
        - id: test-cmd
          type: shell
          command: "pnpm test"
    - id: tsc
      nodes:
        - id: tsc-cmd
          type: shell
          command: "pnpm tsc --noEmit"
```

### 12.2 스키마

| 필드 | 타입 | 필수 | 기본값 | 설명 |
|------|------|------|--------|------|
| `id` | `string` | 예 | — | 파이프라인 내 unique 식별자 |
| `type` | `"parallel"` | 예 | — | 노드 타입 리터럴 |
| `branches` | `BranchSpec[]` | 예 | — | 병렬 실행할 branch 목록 |
| `mergeStrategy` | `MergeStrategy` | 아니오 | `"all_must_pass"` | 결과 통합 방식 |
| `maxConcurrent` | `integer` | 아니오 | `settings.maxParallel` | 동시 실행 최대 branch 수 |
| `onError` | `"abort_all" \| "continue"` | 아니오 | `"abort_all"` | branch 실패 시 나머지 처리 |
| `cancelOnFirstFailure` | `boolean` | 아니오 | `false` | 첫 실패 시 나머지 branch 즉시 취소 |
| `when` | `Condition` | 아니오 | 항상 실행 | 실행 조건 |
| `onFailure` | `FailurePolicy` | 아니오 | 파이프라인 상속 | 실패 시 정책 |

`BranchSpec` 스키마:

| 필드 | 타입 | 필수 | 설명 |
|------|------|------|------|
| `id` | `string` | 예 | branch 식별자 (파이프라인 내 unique) |
| `nodes` | `NodeSpec[]` | 예 | 이 branch 에서 순차 실행할 노드 배열 |

`MergeStrategy` 허용 값:

| 값 | 성공 조건 | `output.data` |
|----|-----------|---------------|
| `all_must_pass` | 모든 branch 가 성공 | 모든 branch 결과 배열 |
| `any_succeeds` | 하나 이상 성공 | 성공한 branch 결과 배열 |
| `majority` | 과반(> 50%) 성공 | 모든 branch 결과 배열 |
| `best_score` | 항상 성공 | 가장 높은 `$score` 를 반환한 branch 결과 |

### 12.3 주요 필드 상세

#### `mergeStrategy` 비교

| 전략 | 사용 사례 | 실패 허용 |
|------|-----------|-----------|
| `all_must_pass` | CI 체크 (lint/test/tsc 모두 통과해야 함) | 0개 |
| `any_succeeds` | 선택적 체크 (최소 하나라도 통과하면 됨) | N-1 개까지 |
| `majority` | 다수결 (3개 중 2개 통과) | ⌊N/2⌋ 개까지 |
| `best_score` | 다중 모델 검증 (가장 좋은 결과 선택) | 무관 (최고 score 선택) |

`best_score` 전략은 branch 내 마지막 노드의 `output.data.score` (number) 를 비교한다. branch 노드들이 `score` 필드를 반환하지 않으면 compile time 경고를 발행한다.

#### `onError` + `cancelOnFirstFailure` 상호작용

| `onError` | `cancelOnFirstFailure` | 동작 |
|-----------|------------------------|------|
| `abort_all` | `false` | 실패한 branch 를 대기, 나머지는 완료까지 실행 후 집계 |
| `abort_all` | `true` | 첫 실패 시 나머지 branch 즉시 취소 → 빠른 실패 |
| `continue` | `false` | 모든 branch 완료 후 mergeStrategy 적용 |
| `continue` | `true` | 첫 실패 감지 후 나머지 취소, 성공한 결과만으로 집계 |

#### `output.data` 구조

```typescript
{
  branches: Array<{
    id: string,
    status: "success" | "failure" | "cancelled",
    output: NodeOutput,    // 해당 branch 마지막 노드의 output
    duration: number       // branch 실행 시간 (ms)
  }>,
  selected?: {             // best_score 전략 시 선택된 branch
    id: string,
    score: number,
    output: NodeOutput
  }
}
```

### 12.4 실전 예시

**예시 1: CI 체크 (lint/test/tsc)**

```yaml
- id: ci-checks
  type: parallel
  mergeStrategy: all_must_pass
  cancelOnFirstFailure: true
  branches:
    - id: lint
      nodes:
        - id: lint-run
          type: shell
          command: "pnpm lint --format=json"
          outputFormat: json
          failOnNonZero: false
    - id: test
      nodes:
        - id: test-run
          type: shell
          command: "pnpm test --reporter=json"
          outputFormat: json
          timeout: 120
    - id: typecheck
      nodes:
        - id: tsc-run
          type: shell
          command: "pnpm tsc --noEmit"
          timeout: 60
```

**예시 2: 다중 모델 검증 (best_score)**

세 모델이 독립적으로 코드를 검증하고, 가장 높은 점수를 반환한 결과를 선택한다.

```yaml
- id: multi-verify
  type: parallel
  mergeStrategy: best_score
  maxConcurrent: 3
  branches:
    - id: claude-verify
      nodes:
        - id: claude-check
          type: agent
          role: verifier
          model: claude-code
          prompt: "코드를 검증하고 JSON 으로 score(0-100)를 반환해주세요."
          output:
            schema:
              score: number
              issues: array
    - id: gemini-verify
      nodes:
        - id: gemini-check
          type: agent
          role: verifier
          model: gemini-cli
          prompt: "코드를 검증하고 JSON 으로 score(0-100)를 반환해주세요."
          output:
            schema:
              score: number
              issues: array
    - id: codex-verify
      nodes:
        - id: codex-check
          type: agent
          role: verifier
          model: codex-cli
          prompt: "코드를 검증하고 JSON 으로 score(0-100)를 반환해주세요."
          output:
            schema:
              score: number
              issues: array
```

**예시 3: 선택적 체크 (any_succeeds)**

성능 테스트, 보안 스캔 중 하나라도 통과하면 진행한다.

```yaml
- id: optional-checks
  type: parallel
  mergeStrategy: any_succeeds
  onError: continue
  cancelOnFirstFailure: false
  branches:
    - id: perf-check
      nodes:
        - id: perf-run
          type: shell
          command: "pnpm benchmark --threshold=100ms"
          failOnNonZero: false
    - id: security-scan
      nodes:
        - id: sec-run
          type: shell
          command: "pnpm audit --audit-level=moderate"
          failOnNonZero: false
```

### 12.5 에러 처리

| 상황 | `mergeStrategy` | 동작 |
|------|-----------------|------|
| branch 하나 실패 | `all_must_pass` | parallel 노드 실패 |
| branch 하나 실패 | `any_succeeds` | 나머지 성공 시 parallel 노드 성공 |
| 과반 실패 | `majority` | parallel 노드 실패 |
| 모든 branch 실패 | `best_score` | parallel 노드 실패 |
| branch cancel (`cancelOnFirstFailure`) | — | 해당 branch `status: "cancelled"`, 결과 없음 |

**취소된 branch 처리**: `onError: abort_all` + `cancelOnFirstFailure: true` 일 때 취소된 branch 는 `output.data.branches[].status = "cancelled"` 로 기록된다. 비용은 취소 시점까지 사용된 토큰만 청구된다.

### 12.6 Anti-patterns

```yaml
# ❌ 의존 관계 있는 작업을 parallel 로 — 순서 보장 없음
branches:
  - id: build
    nodes: [{ id: build-cmd, type: shell, command: "pnpm build" }]
  - id: test
    nodes: [{ id: test-cmd, type: shell, command: "pnpm test" }]
    # test 가 build 결과에 의존하는데 병렬 실행 — build 완료 전에 test 실행될 수 있음

# ✅ 순차 실행 또는 dependsOn 사용 (branch 간 dependsOn 은 지원하지 않음)
# → sequential 로 분리: build → parallel(lint, unit-test)
```

```yaml
# ❌ best_score 인데 branch 들이 score 반환 안 함
mergeStrategy: best_score
branches:
  - id: check-a
    nodes:
      - id: run-a
        type: shell
        command: "pnpm test"
        # output.data 에 score 필드 없음 → best_score 비교 불가

# ✅ score 를 반환하는 agent 노드 사용
branches:
  - id: check-a
    nodes:
      - id: run-a
        type: agent
        output:
          schema:
            score: number
```

```yaml
# ❌ 10+ branches 동시 실행 + maxConcurrent 없음 — 비용/rate limit 폭발
branches:
  - id: model-1
    ...
  - id: model-2
    ...
  # ... 15개 branch

# ✅ maxConcurrent 로 동시 실행 수 제한
maxConcurrent: 3   # 3개씩 순차 실행
```

> 상세 설계: [설계 4B2](../design-docs/17_PhaseP_design4b2_flow_control.md)
