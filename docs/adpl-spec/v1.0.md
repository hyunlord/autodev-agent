## 1. 개요 + 철학

### 1.1 ADPL이란?

**ADPL (AutoDev Pipeline Description Language)** 은 AutoDev Agent 의 파이프라인 실행 동작을 YAML 로 선언하는 언어다. 개발자는 ADPL 파이프라인 파일 하나로 AI 에이전트 호출, 쉘 명령, HTTP 요청, 조건 분기, 병렬 실행 등을 조합하여 반복 가능한 자동화 워크플로를 정의한다.

ADPL 은 AutoDev 의 기존 단일 Task → Plan → Code → Verify 파이프라인을 일반화한 것이다. v1.0 에서는 단일 파이프라인 실행 모드(`pipelineMode: "pipeline"`)를 정의하며, 이후 버전에서 조직 수준 오케스트레이션, 멀티 워크트리 병렬 실행 등으로 확장된다.

### 1.2 핵심 철학

**선언적 YAML 우선**

파이프라인의 "무엇을 할 것인가"와 "어떻게 실행할 것인가"를 분리한다. ADPL 파일은 의도를 선언하며, 실행 엔진이 스케줄링·재시도·에러 처리를 담당한다. 이로써 파이프라인 정의는 실행 환경과 독립적으로 버전 관리·공유·재사용된다.

**언어와 엔진 분리**

ADPL 스펙(이 문서)과 ADPL 엔진 구현은 별개다. 동일한 ADPL 파일을 다른 엔진(예: 로컬 runner, CI 시스템)에서 실행할 수 있도록 인터페이스를 명세한다. 엔진은 스펙을 준수해야 하며, 스펙에 정의되지 않은 동작은 구현 정의(implementation-defined)다.

**확장 가능한 노드 타입**

v1.0 은 `agent`, `shell`, `http`, `webhook_out`, `branch`, `parallel`, `loop`, `gate`, `mcp`, `set` 노드를 기본 제공한다. 향후 플러그인 시스템(v1.5+)을 통해 사용자 정의 노드를 등록할 수 있다. 커스텀 노드는 기본 노드와 동일한 스키마 인터페이스를 준수해야 한다.

**Strangler Fig 패턴으로 legacy 공존**

ADPL 파이프라인 모드(`pipelineMode: "pipeline"`)는 기존 단일 Task 실행 모드(`pipelineMode: "legacy"`)와 공존한다. 기존 Task 는 ADPL 파이프라인 없이도 계속 동작하며, 새 Task 만 ADPL 을 사용하도록 점진적으로 마이그레이션할 수 있다.

### 1.3 Hello World 예시

가장 단순한 ADPL 파이프라인 — 단일 에이전트 호출:

```yaml
adplVersion: 1
name: hello-world
description: 단순한 에이전트 호출 예시

triggers:
  - type: manual

pipeline:
  - id: greet
    type: agent
    prompt: "안녕하세요! 현재 날짜와 간단한 인사말을 작성해주세요."
```

조건 분기를 포함한 예시:

```yaml
adplVersion: 1
name: conditional-review
description: 코드 품질에 따라 분기하는 예시

triggers:
  - type: manual

pipeline:
  - id: analyze
    type: agent
    prompt: "다음 코드를 분석하고 품질 점수(0-100)를 JSON으로 반환해주세요: ${$task.prompt}"
    output:
      schema:
        score: number

  - id: route
    type: branch
    branches:
      - when:
          field: $nodes.analyze.output.data.score
          gte: 80
        goto: approve
      - when:
          field: $nodes.analyze.output.data.score
          lt: 80
        goto: fix

  - id: approve
    type: agent
    prompt: "코드 품질이 양호합니다. 최종 승인 메시지를 작성해주세요."

  - id: fix
    type: agent
    prompt: "코드 품질 개선이 필요합니다. 개선 사항을 구체적으로 제안해주세요."
```

### 1.4 언제 ADPL을 쓰나

| 사용 사례 | 설명 |
|-----------|------|
| **반복 워크플로 자동화** | 코드 리뷰 → 테스트 → 배포 등 정형화된 순서를 파이프라인으로 정의 |
| **조건 분기 처리** | 결과에 따라 다른 에이전트 경로를 선택 (예: 품질 통과/실패 분기) |
| **병렬 에이전트 실행** | 독립적인 작업을 병렬로 처리하여 실행 시간 단축 |
| **외부 시스템 연동** | HTTP 엔드포인트 호출, Webhook 발송, MCP 서버 연동 |

ADPL 을 사용하지 **않는** 경우: 단발성 Task, 간단한 질의응답, 실험적 프롬프트 테스트는 기존 단일 Task 모드로 충분하다.

### 1.5 용어집

| 용어 | 정의 |
|------|------|
| **pipeline** | ADPL 파일 하나가 정의하는 실행 단위. 여러 노드의 순서 있는 집합. |
| **node** | 파이프라인의 최소 실행 단위. `agent`, `shell`, `http` 등 타입을 가짐. |
| **trigger** | 파이프라인 실행을 시작하는 이벤트. `manual`, `webhook`, `schedule` 등. |
| **flow** | `branch`, `parallel`, `loop`, `gate` 등 흐름 제어 노드의 총칭. |
| **adapter** | 외부 시스템(Slack, GitHub 등)과 AutoDev 를 연결하는 플러그인 컴포넌트. |
| **context** | 파이프라인 실행 중 노드가 참조할 수 있는 런타임 변수 집합 (`$task`, `$nodes` 등). |
| **expression** | ADPL 의 값 참조·조건 평가 언어. 3-slot 시스템으로 구성됨. |
| **version** | 동일 파이프라인 이름의 특정 YAML 스냅샷. `pipelineVersions` 테이블에 저장. |
| **project** | AutoDev 의 최상위 작업 단위. 여러 Task 와 파이프라인 버전을 포함. |

## 2. Top-level structure

ADPL 파이프라인 파일의 최상위 구조:

```yaml
adplVersion: 1              # 필수: ADPL 스펙 버전
name: my-pipeline           # 필수: 파이프라인 이름 (프로젝트 내 unique)
description: "..."          # 선택: 파이프라인 설명
triggers:                   # 선택: 실행 트리거 목록 (기본값: manual 1개)
  - type: manual
pipeline:                   # 필수: 노드 배열
  - id: step1
    type: agent
    prompt: "..."
settings:                   # 선택: 파이프라인 레벨 설정
  maxParallel: 3
  totalTimeout: 3600
metadata:                   # 선택: 자유 형식 메타데이터
  owner: team-a
  tags: [review, automation]
```

**최상위 필드 요약**:

| 필드 | 타입 | 필수 | 기본값 |
|------|------|------|--------|
| `adplVersion` | `integer` | 예 | — |
| `name` | `string` | 예 | — |
| `description` | `string` | 아니오 | `""` |
| `triggers` | `array` | 아니오 | `[{ type: manual }]` |
| `pipeline` | `array` | 예 | — |
| `settings` | `object` | 아니오 | 각 필드 기본값 |
| `metadata` | `object` | 아니오 | `{}` |

### 2.1 `adplVersion`

| 항목 | 값 |
|------|-----|
| **타입** | `integer` |
| **필수** | 예 |
| **허용 값** | `1` (v1.0 현재 유일) |
| **기본값** | 없음 (명시 필수) |

`adplVersion` 은 이 파일이 준수하는 ADPL 스펙의 Major 버전을 지정한다. 엔진은 `adplVersion` 값을 확인하여 호환 여부를 판단한다. 지원하지 않는 버전이면 실행을 거부하고 에러를 반환한다.

```yaml
adplVersion: 1
```

> ⚠️ `adplVersion` 필드가 없으면 엔진은 경고를 출력하고 latest 버전으로 해석한다. 명시적 선언을 강권한다.

### 2.2 `name`

| 항목 | 값 |
|------|-----|
| **타입** | `string` |
| **필수** | 예 |
| **허용 값** | `/^[a-z0-9][a-z0-9\-]{0,62}$/` (소문자 알파벳, 숫자, 하이픈, 63자 이하) |
| **기본값** | 없음 |
| **유일성** | 동일 `projectId` 내에서 unique |

파이프라인의 식별자. 버전 관리의 기준이 되므로, 한 번 정해진 이름은 변경하지 않는 것을 권장한다. 이름 변경은 새 파이프라인 생성과 동등하게 취급된다.

```yaml
name: code-review-pipeline
```

### 2.3 `description`

| 항목 | 값 |
|------|-----|
| **타입** | `string` |
| **필수** | 아니오 |
| **최대 길이** | 500자 |
| **기본값** | `""` (빈 문자열) |

사람이 읽기 위한 파이프라인 설명. UI 목록 표시, 검색 등에 활용된다. YAML 멀티라인 문자열 허용.

```yaml
description: |
  코드 품질을 분석하고 개선 사항을 자동으로 제안하는 파이프라인.
  품질 점수 80 미만 시 자동 수정 에이전트를 실행합니다.
```

### 2.4 `triggers`

| 항목 | 값 |
|------|-----|
| **타입** | `array<TriggerObject>` |
| **필수** | 아니오 |
| **기본값** | `[{ type: manual }]` |
| **최소 항목** | 0 (빈 배열 허용, 단 실행 불가) |

파이프라인 실행을 시작하는 이벤트 목록. 여러 트리거를 동시에 정의할 수 있다.

지원 트리거 타입:

| 타입 | 설명 |
|------|------|
| `manual` | 사용자가 UI 또는 API 를 통해 직접 실행 |
| `webhook` | 외부 HTTP POST 요청 수신 |
| `schedule` | cron 표현식 기반 정기 실행 |
| `task_event` | Task 상태 변경 이벤트 (예: Task 완료 시) |

트리거 상세 스펙은 [§15 Triggers](#15-triggers) (Part C) 참조.

```yaml
triggers:
  - type: manual
  - type: schedule
    cron: "0 9 * * 1-5"
    timezone: Asia/Seoul
```

### 2.5 `pipeline`

| 항목 | 값 |
|------|-----|
| **타입** | `array<NodeObject>` |
| **필수** | 예 |
| **최소 항목** | 1 |
| **순서** | 정의 순서대로 실행 (flow 노드가 분기/병렬 결정) |

파이프라인을 구성하는 노드의 배열. 각 노드는 `id` 와 `type` 을 필수로 가진다.

**공통 노드 필드**:

| 필드 | 타입 | 필수 | 기본값 | 설명 |
|------|------|------|--------|------|
| `id` | `string` | 예 | — | 파이프라인 내 unique 식별자 (`/^[a-z0-9][a-z0-9\-_]{0,62}$/`) |
| `type` | `string` | 예 | — | 노드 타입 (`agent`, `shell`, `http`, ...) |
| `name` | `string` | 아니오 | `id` 값 | 사람이 읽기 위한 표시 이름 |
| `description` | `string` | 아니오 | `""` | 노드 설명 |
| `when` | `Condition` | 아니오 | 항상 실행 | 실행 조건 (Slot 2 표현식) |
| `onFailure` | `FailurePolicy` | 아니오 | 파이프라인 설정 상속 | 실패 시 정책 |
| `timeout` | `integer` | 아니오 | `settings.nodeTimeout` | 노드 단위 타임아웃 (초) |
| `retryPolicy` | `RetryPolicy` | 아니오 | 없음 | 재시도 설정 |
| `dependsOn` | `string[]` | 아니오 | `[]` | 명시적 의존 노드 목록 |

```yaml
pipeline:
  - id: plan
    type: agent
    prompt: "구현 계획을 수립해주세요: ${$task.prompt}"

  - id: implement
    type: agent
    prompt: "다음 계획을 구현해주세요: ${$nodes.plan.output.data}"
    dependsOn: [plan]

  - id: verify
    type: shell
    command: "pnpm test"
    dependsOn: [implement]
```

### 2.6 `settings`

| 항목 | 값 |
|------|-----|
| **타입** | `object` |
| **필수** | 아니오 |
| **기본값** | 아래 각 필드 기본값 참조 |

파이프라인 레벨 실행 설정. 노드 단위 설정이 우선한다.

| 필드 | 타입 | 기본값 | 허용 범위 | 설명 |
|------|------|--------|-----------|------|
| `maxParallel` | `integer` | `5` | 1–20 | 동시 실행 가능한 최대 노드 수 |
| `totalTimeout` | `integer` | `7200` | 1–86400 | 파이프라인 전체 타임아웃 (초) |
| `nodeTimeout` | `integer` | `600` | 1–3600 | 노드 단위 기본 타임아웃 (초) |
| `onNodeFailure` | `FailurePolicy` | `"abort"` | abort\|continue\|retry | 노드 실패 시 기본 정책 |
| `totalCostLimit` | `number \| null` | `null` | > 0 | 파이프라인 총 비용 한도 (USD) |
| `retryPolicy` | `RetryPolicy \| null` | `null` | — | 파이프라인 기본 재시도 정책 |
| `allowedEnvKeys` | `string[]` | `[]` | — | `$env` 에서 접근 허용된 환경 변수 키 목록 |

`FailurePolicy` 허용 값:

| 값 | 동작 |
|----|------|
| `"abort"` | 파이프라인 즉시 중단, 후속 노드 실행 안 함 |
| `"continue"` | 실패 노드를 `skipped` 로 표시하고 후속 노드 계속 실행 |
| `"retry"` | `retryPolicy` 에 따라 재시도 후 실패 시 `abort` |

`RetryPolicy` 스키마:

```yaml
retryPolicy:
  maxAttempts: 3        # 최대 시도 횟수 (초기 실행 포함, 기본값: 1)
  backoff: exponential  # linear | exponential | fixed
  initialDelay: 5       # 첫 재시도 대기 시간 (초)
  maxDelay: 60          # 최대 대기 시간 (초)
```

```yaml
settings:
  maxParallel: 3
  totalTimeout: 3600
  onNodeFailure: continue
  totalCostLimit: 1.00
  allowedEnvKeys:
    - GITHUB_TOKEN
    - SLACK_WEBHOOK_URL
```

### 2.7 `metadata`

| 항목 | 값 |
|------|-----|
| **타입** | `object` (자유 형식) |
| **필수** | 아니오 |
| **기본값** | `{}` |

엔진이 해석하지 않는 자유 형식 메타데이터. UI 표시, 태깅, 외부 시스템 연동 등에 활용한다.

```yaml
metadata:
  owner: platform-team
  tags:
    - code-quality
    - automation
  version: "2.1.0"
```

> ⚠️ `metadata` 의 값은 ADPL 표현식으로 평가되지 않는다. 정적 값만 허용한다.

### 2.8 전체 예시

필드 조합의 전형적인 예:

```yaml
adplVersion: 1
name: full-review-pipeline
description: 코드 리뷰 + 자동 수정 + 검증 파이프라인

triggers:
  - type: manual
  - type: webhook
    secret: "${$env.WEBHOOK_SECRET}"

pipeline:
  - id: review
    type: agent
    prompt: |
      다음 코드를 리뷰하고 JSON 형식으로 결과를 반환해주세요.
      코드: ${$task.prompt}
    output:
      schema:
        score: number
        issues: array

  - id: check-quality
    type: branch
    branches:
      - when:
          field: $nodes.review.output.data.score
          gte: 80
        goto: approve
      - else: true
        goto: fix

  - id: fix
    type: agent
    prompt: "다음 이슈를 수정해주세요: ${$nodes.review.output.data.issues | json}"

  - id: approve
    type: shell
    command: "echo 'Quality passed'"

settings:
  maxParallel: 2
  totalTimeout: 1800
  onNodeFailure: abort
  totalCostLimit: 0.50

metadata:
  owner: code-quality-team
  tags: [review, automated]
```

## 3. 컨텍스트 변수

파이프라인 실행 중 모든 표현식에서 접근 가능한 런타임 변수 집합. 네임스페이스(`$task`, `$nodes` 등)로 구분된다.

### 3.1 `$task`

현재 실행 중인 Task 의 정보. 파이프라인 실행 전체에서 접근 가능.

| 필드 | 타입 | 설명 |
|------|------|------|
| `$task.id` | `string` | Task 고유 ID (nanoid) |
| `$task.prompt` | `string` | Task 에 입력된 원본 프롬프트 |
| `$task.tags` | `string[]` | Task 태그 목록 |
| `$task.createdAt` | `string` | Task 생성 시각 (ISO 8601) |
| `$task.pipelineMode` | `string` | `"pipeline"` 또는 `"legacy"` |
| `$task.projectId` | `string \| null` | 연결된 프로젝트 ID |
| `$task.pipelineVersionId` | `string \| null` | 실행 중인 파이프라인 버전 ID |
| `$task.status` | `string` | 현재 Task 상태 |
| `$task.config` | `object` | Task 생성 시 전달된 설정 객체 |

```yaml
- id: process
  type: agent
  prompt: "다음 요청을 처리해주세요: ${$task.prompt}"
```

### 3.2 `$project`

현재 Task 가 속한 Project 의 정보.

| 필드 | 타입 | 설명 |
|------|------|------|
| `$project.id` | `string` | 프로젝트 고유 ID |
| `$project.name` | `string` | 프로젝트 이름 |
| `$project.path` | `string` | 프로젝트 루트 절대 경로 |
| `$project.description` | `string \| null` | 프로젝트 설명 |
| `$project.createdAt` | `string` | 프로젝트 생성 시각 (ISO 8601) |

> ⚠️ `$task.projectId` 가 `null` 이면 `$project` 의 모든 필드는 `null` 을 반환한다.

```yaml
- id: analyze
  type: agent
  prompt: "프로젝트 ${$project.name} (${$project.path}) 의 코드를 분석해주세요."
```

### 3.3 `$nodes`

완료된 노드의 실행 결과에 접근한다. **가장 중요한 컨텍스트 네임스페이스**.

```
$nodes.<nodeId>.output.status    # "success" | "failure" | "skipped"
$nodes.<nodeId>.output.data      # 노드가 반환한 데이터 (노드 타입별 상이)
$nodes.<nodeId>.output.error     # 실패 시 에러 정보 (status = "failure" 일 때)
$nodes.<nodeId>.output.duration  # 실행 소요 시간 (ms)
$nodes.<nodeId>.output.costUsd   # agent 노드의 경우 비용 (USD)
```

**접근 규칙**:

| 규칙 | 설명 |
|------|------|
| **순서 제약** | 현재 노드보다 **앞에 정의된 노드**만 접근 가능 |
| **완료 상태** | `status` 가 `success`, `failure`, `skipped` 인 노드만 접근 가능 |
| **pending/running 접근** | 에러: `ReferenceError: node 'X' is not yet completed` |
| **미존재 노드 접근** | 저장 단계에서 검증 실패 (Compile time error) |

**`output.data` 타입**:

| 노드 타입 | `output.data` 타입 |
|-----------|---------------------|
| `agent` | `string` 또는 `output.schema` 정의 시 해당 구조 |
| `shell` | `{ stdout: string, stderr: string, exitCode: number }` |
| `http` | `{ status: number, headers: object, body: unknown }` |
| `set` | 설정된 변수 값 |

```yaml
- id: plan
  type: agent
  prompt: "구현 계획을 수립해주세요."

- id: implement
  type: agent
  prompt: |
    다음 계획을 구현해주세요:
    ${$nodes.plan.output.data}
  when:
    field: $nodes.plan.output.status
    eq: success
```

### 3.4 `$loop`

`loop` 노드 내부의 노드에서만 접근 가능. 현재 반복 컨텍스트를 제공한다.

| 필드 | 타입 | 설명 |
|------|------|------|
| `$loop.index` | `integer` | 현재 반복 인덱스 (0부터 시작) |
| `$loop.total` | `integer` | 총 반복 횟수 |
| `$loop.isFirst` | `boolean` | 첫 번째 반복 여부 |
| `$loop.isLast` | `boolean` | 마지막 반복 여부 |
| `$loop.<as>` | `unknown` | `loop.as` 로 지정한 이름의 현재 아이템 |

> ⚠️ `loop` 노드 외부에서 `$loop` 접근 시 에러: `ReferenceError: $loop is not available outside a loop node`

```yaml
- id: process-items
  type: loop
  items: "${$task.config.files}"
  as: file
  pipeline:
    - id: analyze-file
      type: agent
      prompt: |
        파일 ${$loop.index + 1}/${$loop.total}: ${$loop.file}
        이 파일을 분석해주세요.
```

### 3.5 `$flow`

`branch`, `parallel`, `gate` 등 flow 노드 내부에서 추가 컨텍스트를 제공한다.

**`branch` 내부**:

| 필드 | 타입 | 설명 |
|------|------|------|
| `$flow.matchedBranch` | `string` | 선택된 branch 의 `id` 또는 인덱스 |

**`parallel` 내부**:

| 필드 | 타입 | 설명 |
|------|------|------|
| `$flow.parallelIndex` | `integer` | 병렬 실행 중 현재 브랜치 인덱스 |
| `$flow.parallelTotal` | `integer` | 병렬 실행 총 브랜치 수 |

**`gate` 내부**:

| 필드 | 타입 | 설명 |
|------|------|------|
| `$flow.gateStatus` | `string` | `"pending"` \| `"approved"` \| `"rejected"` |
| `$flow.gateRespondedBy` | `string \| null` | 승인/거절한 사용자 ID |

### 3.6 `$env`

프로젝트 또는 시스템 레벨에서 설정된 환경 변수에 접근한다.

**접근 규칙**:

| 규칙 | 설명 |
|------|------|
| **Allowlist 필수** | `settings.allowedEnvKeys` 에 포함된 키만 접근 가능 |
| **미승인 키 접근** | 에러: `SecurityError: env key 'X' is not in allowedEnvKeys` |
| **미존재 키** | `null` 반환 (에러 아님) |
| **로그 마스킹** | `$env.*` 값은 로그·UI 에서 자동으로 `***` 로 마스킹 |

```yaml
settings:
  allowedEnvKeys:
    - GITHUB_TOKEN

pipeline:
  - id: github-api
    type: http
    url: "https://api.github.com/repos/owner/repo"
    headers:
      Authorization: "Bearer ${$env.GITHUB_TOKEN}"
```

### 3.7 `$trigger`

파이프라인을 실행시킨 트리거의 정보.

**공통 필드**:

| 필드 | 타입 | 설명 |
|------|------|------|
| `$trigger.type` | `string` | 트리거 타입 (`manual`, `webhook`, `schedule`, `task_event`) |
| `$trigger.firedAt` | `string` | 트리거 발동 시각 (ISO 8601) |

**`webhook` 트리거 추가 필드**:

| 필드 | 타입 | 설명 |
|------|------|------|
| `$trigger.payload` | `object` | HTTP 요청 body (JSON 파싱된 값) |
| `$trigger.headers` | `object` | HTTP 요청 헤더 (소문자 키) |
| `$trigger.sourceIp` | `string` | 요청 발신 IP |

**`schedule` 트리거 추가 필드**:

| 필드 | 타입 | 설명 |
|------|------|------|
| `$trigger.scheduledAt` | `string` | cron 스케줄 기준 실행 예정 시각 (ISO 8601) |

```yaml
- id: handle-webhook
  type: agent
  prompt: |
    ${$trigger.payload.event} 이벤트를 처리해주세요.
    페이로드: ${$trigger.payload | json}
```

## 4. 표현식 3-slot 시스템

ADPL 은 세 가지 표현식 슬롯을 제공한다. 각 슬롯은 사용 위치와 목적이 다르다.

| 슬롯 | 이름 | 문법 | 주요 사용 위치 |
|------|------|------|---------------|
| Slot 1 | 보간 (Interpolation) | `${...}` | 문자열 값 안 |
| Slot 2 | 조건 (Condition) | 구조화 객체 또는 문자열 | `when`, `condition`, `filter` 필드 |
| Slot 3 | 변환 (Transform) | — | **v1.5 유보** |

### 4.1 Slot 1: 보간 (Interpolation)

문자열 값 안에 `${...}` 구문으로 런타임 값을 삽입한다.

**기본 문법**:

```
${<expression>}
${<expression> | <filter>}
${<expression> | <filter1> | <filter2>}
${<expression> ?? <fallback>}
```

**예시**:

```yaml
prompt: "작업: ${$task.prompt}"
prompt: "점수: ${$nodes.review.output.data.score | round}"
prompt: "태그: ${$task.tags | join(', ')}"
prompt: "요약: ${$nodes.analyze.output.data ?? '(결과 없음)'}"
```

**내장 필터 20개**:

| 필터 | 설명 | 예시 |
|------|------|------|
| `truncate(n)` | n 자로 잘라냄 | `${text \| truncate(100)}` |
| `lower` | 소문자 변환 | `${$task.prompt \| lower}` |
| `upper` | 대문자 변환 | `${status \| upper}` |
| `json` | JSON 직렬화 | `${data \| json}` |
| `round` | 반올림 (정수) | `${score \| round}` |
| `toFixed(n)` | 소수점 n자리 | `${cost \| toFixed(4)}` |
| `replace(a, b)` | 문자열 치환 | `${text \| replace('old', 'new')}` |
| `slice(s, e)` | 배열/문자열 슬라이스 | `${list \| slice(0, 3)}` |
| `default(v)` | null/undefined 시 기본값 | `${name \| default('익명')}` |
| `join(sep)` | 배열을 문자열로 | `${tags \| join(', ')}` |
| `length` | 길이 반환 | `${text \| length}` |
| `escape` | HTML 이스케이프 | `${html \| escape}` |
| `urlencode` | URL 인코딩 | `${param \| urlencode}` |
| `jsonParse` | JSON 파싱 | `${jsonStr \| jsonParse}` |
| `toDate` | ISO 8601 → 날짜 포맷 | `${createdAt \| toDate}` |
| `toTime` | ISO 8601 → 시간 포맷 | `${firedAt \| toTime}` |
| `padStart(n, c)` | 앞 패딩 | `${num \| padStart(3, '0')}` |
| `padEnd(n, c)` | 뒤 패딩 | `${code \| padEnd(10, ' ')}` |
| `trim` | 앞뒤 공백 제거 | `${text \| trim}` |
| `capitalize` | 첫 글자 대문자 | `${name \| capitalize}` |

**Nullish Fallback (`??`)**:

표현식 결과가 `null` 또는 `undefined` 일 때 대체값을 사용한다:

```yaml
prompt: "결과: ${$nodes.analyze.output.data.summary ?? '분석 결과가 없습니다.'}"
```

> ⚠️ **삼항 연산자 없음**: `${ condition ? a : b }` 문법은 지원하지 않는다. 조건 분기는 `branch` 노드 또는 `when` 필드를 사용하라.

**Anti-pattern**:

```yaml
# ❌ 삼항 연산자 — 지원 안 함
prompt: "${score >= 80 ? '통과' : '실패'}"

# ✅ branch 노드로 분기
- id: route
  type: branch
  branches:
    - when:
        field: $nodes.review.output.data.score
        gte: 80
      goto: approve
    - else: true
      goto: reject
```

### 4.2 Slot 2: 구조화 조건 (Structured conditions)

`when`, `condition`, `filter` 필드에서 YAML/JSON 구조로 조건을 표현한다. 코드 없이 조건을 명시할 수 있어 검증·직렬화가 용이하다.

**단일 조건**:

```yaml
when:
  field: $nodes.analyze.output.data.score
  gte: 80
```

**15개 연산자**:

| 연산자 | 입력 타입 | 설명 |
|--------|-----------|------|
| `eq` | any | 같음 (`===`) |
| `neq` | any | 다름 (`!==`) |
| `lt` | number | 미만 |
| `lte` | number | 이하 |
| `gt` | number | 초과 |
| `gte` | number | 이상 |
| `in` | array | 배열 내 포함 |
| `nin` | array | 배열 내 미포함 |
| `contains` | string | 부분 문자열 포함 |
| `startsWith` | string | 특정 문자열로 시작 |
| `endsWith` | string | 특정 문자열로 끝 |
| `matches` | string (regex) | 정규식 매칭 |
| `exists` | — | null/undefined 가 아님 |
| `empty` | — | null, undefined, 빈 문자열, 빈 배열 |
| `truthy` | — | 논리적으로 참 |

**복합 조건**:

```yaml
# AND (all)
when:
  all:
    - field: $nodes.review.output.data.score
      gte: 70
    - field: $nodes.review.output.data.issues
      empty: true

# OR (any)
when:
  any:
    - field: $task.tags
      contains: urgent
    - field: $nodes.analyze.output.data.severity
      eq: critical

# NOT
when:
  not:
    field: $nodes.gate.output.status
    eq: rejected
```

**조건 내 변환 (`lower`, `upper`, `length`)**:

```yaml
when:
  field: $task.prompt
  transform: lower
  contains: "bug fix"
```

**중첩 복합 조건 예시**:

```yaml
when:
  all:
    - field: $nodes.test.output.data.exitCode
      eq: 0
    - field: $nodes.lint.output.data.errors
      transform: length
      eq: 0
    - any:
        - field: $task.tags
          in: [hotfix, urgent]
        - field: $task.config.priority
          gte: 8
```

### 4.3 Slot 2: 문자열 조건 (String conditions)

구조화 조건과 동등하며, 자연스러운 문자열 표현을 사용한다. Jexl 기반 파서(또는 자체 구현)로 평가된다.

**문법**:

```yaml
when: "$nodes.review.output.data.score >= 80"
when: "$task.tags contains 'urgent' and $nodes.plan.output.status == 'success'"
when: "$nodes.test.output.data.exitCode == 0 or $task.config.skipTest == true"
```

**허용 연산자**:

| 연산자 | 설명 |
|--------|------|
| `==`, `!=` | 동등 비교 |
| `<`, `<=`, `>`, `>=` | 크기 비교 |
| `contains` | 문자열/배열 포함 |
| `startsWith`, `endsWith` | 문자열 시작/끝 |
| `matches` | 정규식 매칭 (`/pattern/` 문법) |
| `in` | 배열 포함 (`x in [a, b, c]`) |
| `and`, `or`, `not` | 논리 연산 |
| `(...)` | 괄호 그룹 |

**허용 함수**:

| 함수 | 설명 |
|------|------|
| `length(x)` | 길이 |
| `lower(x)` | 소문자 |
| `upper(x)` | 대문자 |
| `exists(x)` | 존재 여부 |
| `empty(x)` | 빈 값 여부 |

**구조화 조건과 동등 예시**:

```yaml
# 문자열 조건
when: "$nodes.analyze.output.data.score >= 80 and $nodes.lint.output.data.errors == 0"

# 위와 동등한 구조화 조건
when:
  all:
    - field: $nodes.analyze.output.data.score
      gte: 80
    - field: $nodes.lint.output.data.errors
      eq: 0
```

**문자열 조건 추가 예시**:

```yaml
# 복합 논리
when: "(length($nodes.issues.output.data) == 0) or ($task.config.force == true)"

# 정규식 사용
when: "$task.prompt matches /^(fix|hotfix):/i"

# 배열 포함
when: "$task.tags in ['critical', 'p0', 'p1']"

# 함수 조합
when: "lower($nodes.agent.output.data) contains 'error' and exists($task.config.debug)"
```

> ⚠️ 문자열 조건은 구조화 조건보다 파싱 복잡도가 높아 저장 단계 검증이 덜 정확할 수 있다. 프로그래매틱 생성 시 구조화 조건을 권장한다.

### 4.4 Slot 3: 변환 (Transform) — v1.5 유보

> **이 슬롯은 ADPL v1.0 에서 정의하지 않는다.**

v1.0 에서 데이터 변환이 필요한 경우:

- `set` 노드로 값 설정: [§17 보조 노드](#17-보조-노드-set-transform) (Part C) 참조
- Slot 1 필터로 포맷 변환
- `agent` 노드에 변환 로직 포함

Slot 3 (`transform` 노드 타입) 은 v1.5 에서 공식 도입 예정이다.

### 4.5 표현식 사용 위치

| 위치 | Slot | 설명 |
|------|------|------|
| 문자열 필드 값 안 `${...}` | Slot 1 | `prompt`, `url`, `command`, `headers.*` 등 |
| `when` 필드 | Slot 2 | 노드 실행 조건 |
| `condition` 필드 | Slot 2 | `branch` 노드의 분기 조건 |
| `filter` 필드 | Slot 2 | `loop` 노드의 아이템 필터 |
| `items` 필드 | Slot 1 | `loop` 노드의 반복 대상 배열 (`${...}` 로 참조) |
| `goto` 필드 | — | 정적 문자열만 허용 (표현식 불가) |
| `metadata.*` | — | 표현식 미지원 (정적 값만) |

### 4.6 에러 처리

**파싱 에러 (저장 단계)**:

| 상황 | 에러 타입 | 예시 |
|------|-----------|------|
| `${` 는 있으나 `}` 없음 | `ParseError` | `${$task.prompt` |
| 미지원 필터 | `ParseError` | `${text \| unknownFilter}` |
| Slot 2 문자열 문법 오류 | `ParseError` | `when: "score > "` |
| `$nodes.X` — X 가 파이프라인에 없음 | `ReferenceError` | `$nodes.nonexistent` |

**런타임 에러**:

| 상황 | 에러 타입 | 기본 동작 |
|------|-----------|-----------|
| `$nodes.X` 에서 X 가 아직 완료 안 됨 | `ReferenceError` | 파이프라인 실패 |
| 타입 미스매치 (예: 숫자 필터를 문자열에) | `TypeError` | `onFailure` 정책에 따름 |
| `$env.X` 가 allowlist 에 없음 | `SecurityError` | 파이프라인 실패 |
| `$env.X` 가 존재하지 않음 | — | `null` 반환 (에러 아님) |
| `$loop.*` 를 loop 외부에서 접근 | `ReferenceError` | 파이프라인 실패 |

**복구 정책**:

- **Slot 1 보간 에러**: 기본적으로 파이프라인 실패 (`abort`). `?? fallback` 을 사용하면 런타임 에러 대신 fallback 값 사용.
- **Slot 2 조건 에러**: 기본적으로 조건이 `false` 로 평가 (파이프라인은 계속 실행). 단, `ReferenceError` 와 `SecurityError` 는 파이프라인을 실패시킨다.

```yaml
# ?? fallback 으로 런타임 에러 방지
prompt: "이전 결과: ${$nodes.prev.output.data.summary ?? '결과 없음'}"
```

## 5. 에러 + 검증 규칙

ADPL 검증은 **저장 단계 (Compile time)** 와 **런타임 단계 (Run time)** 두 단계로 이루어진다.

### 5.1 저장 단계 검증 (Compile time)

파이프라인 YAML 을 저장·등록할 때 수행하는 정적 검증.

**5.1.1 YAML 파싱**

유효한 YAML 문법이어야 한다. YAML 파싱 실패 시 즉시 거부.

**5.1.2 Zod 스키마 검증**

최상위 필드 및 각 노드 타입별 Zod 스키마를 통과해야 한다.

- `adplVersion`: 정수, 1 이상
- `name`: 정규식 `/^[a-z0-9][a-z0-9\-]{0,62}$/`
- `pipeline`: 배열, 최소 1개 항목
- 각 노드의 `type` 별 필수 필드 존재 확인

**5.1.3 참조 검증**

- `$nodes.X` 에서 `X` 가 동일 파이프라인 내에 존재해야 함
- `goto: X` 에서 `X` 가 동일 파이프라인 내에 존재해야 함
- `dependsOn: [X]` 에서 `X` 가 존재해야 함

**5.1.4 순서 제약 (Forward reference 금지)**

`$nodes.X` 는 현재 노드보다 **앞에 정의된 노드**만 참조 가능. 역방향 참조는 compile time 에러.

```yaml
# ❌ compile time error: 'implement' 는 'plan' 보다 뒤에 정의됨
- id: plan
  type: agent
  prompt: "${$nodes.implement.output.data}"  # 아직 실행 안 된 노드 참조

- id: implement
  type: agent
  prompt: "..."
```

**5.1.5 Cycle 감지**

`dependsOn` 관계에서 순환 의존이 있으면 거부.

**5.1.6 Node ID 유일성**

동일 파이프라인 내 `id` 는 unique 해야 함. 중첩 파이프라인(loop, branch 내부)의 노드 ID 도 전체 파이프라인 내에서 unique 를 권장하며, 충돌 시 경고를 발행한다.

**5.1.7 Shell 노드 검증**

`shell` 노드의 `command` 가 프로젝트 설정의 `allowlist` 에 있는지, `denylist` 에 없는지 확인. 미설정 시 경고만 출력하고 허용한다.

### 5.2 런타임 검증 (Run time)

파이프라인 실행 중 수행하는 동적 검증.

**에러 분류 체계**:

| 분류 | 코드 | 설명 | 재시도 가능 |
|------|------|------|------------|
| `transient` | `ERR_TRANSIENT` | 일시적 실패 (네트워크, rate limit) | 예 |
| `persistent` | `ERR_PERSISTENT` | 영구적 실패 (잘못된 입력, 권한 없음) | 아니오 |
| `quality` | `ERR_QUALITY` | 품질 기준 미달 (LLM 응답 schema 불일치) | 예 |
| `cost_limit` | `ERR_COST_LIMIT` | `totalCostLimit` 초과 | 아니오 |
| `cancellation` | `ERR_CANCELLED` | 사용자 또는 시스템에 의한 취소 | 아니오 |
| `policy_violation` | `ERR_POLICY` | 보안 정책 위반 (allowlist/denylist) | 아니오 |
| `timeout` | `ERR_TIMEOUT` | 타임아웃 초과 | 예 (설정에 따라) |

**타임아웃**:

- 노드 단위: `settings.nodeTimeout` 또는 노드의 `timeout` 필드 (초)
- 파이프라인 전체: `settings.totalTimeout` (초)
- 타임아웃 시 노드 상태 → `failure`, 에러 코드 `ERR_TIMEOUT`

### 5.3 에러 전파 규칙

**노드 레벨 `onFailure` 정책** (파이프라인 `settings.onNodeFailure` 를 override):

| 값 | 동작 |
|----|------|
| `"abort"` | 파이프라인 즉시 중단 |
| `"continue"` | 현재 노드를 `skipped` 상태로 표시, 후속 노드 계속 |
| `"retry"` | 노드의 `retryPolicy` 에 따라 재시도, 모두 실패 시 `abort` |

**우선순위**: 노드 `onFailure` > 파이프라인 `settings.onNodeFailure`

**Flow 노드 집계 규칙**:

| Flow 타입 | 실패 조건 | 설정으로 변경 가능 |
|-----------|-----------|-------------------|
| `branch` | 선택된 브랜치 내 노드 실패 = branch 노드 실패 | — |
| `parallel` | 하나라도 실패 시 (기본값) | `failFast: false` 설정 시 모두 완료 후 집계 |
| `loop` | 하나라도 실패 시 (기본값) | `continueOnError: true` 설정 시 계속 |
| `gate` | `rejected` 상태 = gate 노드 실패 | — |

### 5.4 에러 메시지 포맷

모든 ADPL 에러는 다음 구조를 따른다:

```typescript
interface AdplError {
  code: string;         // 에러 코드 (예: "ERR_REFERENCE")
  category: string;     // 에러 분류 (예: "compile_time")
  location: {
    nodeId?: string;    // 에러 발생 노드 ID
    field?: string;     // 에러 발생 필드 경로 (예: "when.field")
    line?: number;      // YAML 내 줄 번호 (가능한 경우)
  };
  message: string;      // 사람이 읽을 수 있는 에러 메시지
  suggestion?: string;  // 수정 제안 (typo 감지 등)
}
```

**에러 메시지 예시**:

```
[ERR_DUPLICATE_ID] 파이프라인 내 노드 ID 'analyze' 가 중복됩니다.
  위치: pipeline[3].id
  제안: 'analyze-2' 또는 'analyze-final' 등 고유한 이름을 사용하세요.

[ERR_FORWARD_REF] 노드 'plan' 에서 아직 실행되지 않은 노드 'implement' 를 참조합니다.
  위치: pipeline[0].prompt (표현식: $nodes.implement.output.data)
  제안: 'implement' 를 'plan' 보다 앞에 정의하거나, 표현식을 제거하세요.

[ERR_UNKNOWN_NODE] 존재하지 않는 노드 'analyse' 를 참조합니다.
  위치: pipeline[2].when.field
  제안: 'analyze' 를 의도한 것인가요? (유사 이름 감지)

[ERR_POLICY] 환경 변수 'AWS_SECRET_KEY' 는 allowedEnvKeys 에 없습니다.
  위치: pipeline[1].command
  제안: settings.allowedEnvKeys 에 'AWS_SECRET_KEY' 를 추가하세요.

[ERR_COST_LIMIT] 파이프라인 총 비용 한도 $0.50 를 초과했습니다 (현재: $0.53).
  위치: pipeline[4] (agent 노드 'final-summary')
  동작: 파이프라인이 중단되었습니다.

[ERR_TIMEOUT] 노드 'long-running-agent' 가 600초 타임아웃을 초과했습니다.
  위치: pipeline[2]
  제안: 노드의 timeout 필드를 늘리거나, 작업을 더 작은 단위로 분할하세요.
```

## 6. 버전 호환성

### 6.1 adplVersion 필드

ADPL 은 Semantic Versioning 을 따르며, `adplVersion` 필드는 Major 버전을 지정한다.

| 버전 구성 | 의미 |
|-----------|------|
| **Major** (`X.0.0`) | 하위 호환 불가 변경. `adplVersion` 값 증가. |
| **Minor** (`1.X.0`) | 하위 호환 추가. `adplVersion` 값 유지. |
| **Patch** (`1.0.X`) | 버그 수정. 사용자 파일 변경 불필요. |

`adplVersion: 1` 파일은 ADPL 1.x.x 의 모든 Minor/Patch 버전 엔진에서 동작한다.

### 6.2 Minor vs Major 변경 정의

**Minor 변경** (하위 호환, `adplVersion` 유지):

- 새 노드 타입 추가 (예: `mcp`, `gate`)
- 기존 노드에 선택적 필드 추가
- 새 필터/연산자 추가
- 새 컨텍스트 변수 추가
- 성능 개선

**Major 변경** (하위 호환 불가, `adplVersion` 증가):

- 필수 필드 추가 또는 기존 필드 삭제
- 필드 이름 변경 (rename)
- 기본값 변경 (동작 변화를 초래하는 경우)
- 연산자 의미 변경
- 컨텍스트 변수 구조 변경

### 6.3 마이그레이션 정책

**자동 마이그레이션 (Minor)**:

Minor 변경에서 새 필드의 기본값이 이전 동작과 동일하도록 설계한다. 기존 파이프라인 파일은 수정 없이 새 엔진에서 동작한다.

**수동 마이그레이션 (Major)**:

Major 버전 업그레이드 시:
1. 엔진이 `adplVersion` 불일치를 감지하고 에러 반환
2. 마이그레이션 가이드 문서 제공
3. (v1.5 예정) `autodev pipeline migrate --from 1 --to 2` CLI 명령으로 자동 변환

### 6.4 Deprecation 3단계

| 단계 | 기간 | 동작 |
|------|------|------|
| **Phase 1: Deprecated** | Minor 1개 이상 | 기능 동작하되 경고 로그 출력 |
| **Phase 2: Legacy** | Minor 1개 이상 | 기능 동작하되 UI 경고 + migration 강력 권고 |
| **Phase 3: Removed** | Major 버전 | 기능 제거, 실행 시 에러 |

Deprecated 기능은 최소 2개의 Minor 버전 동안 유지된다. Phase 3 제거는 반드시 Major 버전 업그레이드와 함께 이루어진다.

### 6.5 현재 버전: v1.0

| 항목 | 값 |
|------|-----|
| **스펙 버전** | 1.0.0 |
| **발행일** | 2026-04-19 |
| **상태** | 공식 (Stable) |
| **`adplVersion` 값** | `1` |

**v1.0 정책**:

- v1.x 기간 동안 Major 변경 없음 (최소 1년, v1.x 완료 후 검토)
- Minor 추가는 분기별 검토 후 발행
- 모든 Breaking change 는 v2.0 으로 집적
